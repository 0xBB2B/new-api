# 订阅用量轮询调度

## 目的
让每个订阅渠道（Codex、Claude 订阅）的用量快照按"距上次成功更新满 1 小时"各自刷新，管理员手动刷新后自动轮询顺延，既不重复拉取也不让失败渠道频繁打上游。

## 逻辑
- 适用渠道：类型为 Codex 或 Claude 订阅，状态为启用或自动禁用；multi-key 渠道跳过。
- 快照落库：每次成功拉取用量（无论后台轮询还是管理员手动刷新）都把摘要写入渠道 `other_info.subscription_usage`，其中 `updated_at` 为本次成功时刻（Unix 秒）。拉取失败不写快照，`updated_at` 保持原值。
- 后台任务仅在 master 节点运行；启动时立即执行一次扫描，之后每 1 分钟 tick 一次。
- 每次 tick 遍历适用渠道，同时满足以下两条才对该渠道发起拉取：
  1. 渠道没有快照，或 `now - updated_at ≥ 1 小时`；
  2. 本进程距上次对该渠道发起拉取尝试（无论成功失败）≥ 1 小时。
- 拉取尝试时刻只记录在 master 进程内存，进程重启后清零；快照 `updated_at` 存于数据库，重启不受影响。
- 手动刷新入口的行为不变：立即拉取一次，成功即写快照。它对轮询的唯一影响是刷新了 `updated_at`。
- 单个渠道拉取失败只记录警告，不影响同一 tick 内其它渠道。

## 约束
- 同一渠道相邻两次成功快照之间的自动拉取间隔 ≥ 1 小时，误差不超过 1 个 tick（1 分钟）。
- 同一渠道相邻两次拉取尝试（含失败）在同一 master 进程内间隔 ≥ 1 小时。
- 手动刷新成功会把该渠道的下一次自动拉取推迟到手动成功时刻 + 1 小时；1 小时内再次手动成功则再次顺延。
- 手动刷新失败不影响自动拉取时点。

## 例子
- 渠道 A 自动拉取于 10:23 成功 → 11:23 的 tick 再次拉取；10:24～11:22 的每次 tick 都跳过 A。
- 渠道 A 11:23 自动成功，管理员 11:50 手动刷新成功 → 12:23 的 tick 跳过（距 11:50 仅 33 分钟），12:50 的 tick 拉取。
- 管理员 11:50 与 12:30 各手动刷新成功一次 → 下一次自动拉取在 13:30。
- 管理员 11:50 手动刷新时上游返回 401，快照未更新（仍为 11:23）→ 12:23 的 tick 照常拉取。
- 渠道 B 11:23 自动拉取失败（快照仍是 10:23 的）→ 11:24～12:22 的 tick 均跳过 B，12:23 重试。
- 服务 12:00 重启，渠道 A 的快照 `updated_at` 为 11:50 → 启动扫描跳过 A，12:50 的 tick 拉取。
- 服务 12:00 重启，渠道 B 无快照 → 启动扫描立即拉取 B。

## 验收
- [ ] 无快照或快照满 1 小时的渠道在下一 tick 被拉取；不满 1 小时的渠道被跳过。
- [ ] 手动刷新成功后，该渠道自动拉取时点顺延到手动成功 + 1 小时，多次手动则多次顺延。
- [ ] 拉取失败的渠道在同一进程内 1 小时内不再重试；重启后按快照 `updated_at` 判定。
- [ ] tick 间隔为 1 分钟，仅 master 节点运行，multi-key 渠道跳过。
