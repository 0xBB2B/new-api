# 订阅渠道用量轮询

## 目的

为用量均衡路由提供每个启用状态订阅渠道的官方口径瓶颈使用率。

## 逻辑

后台定时任务仅在 master 节点运行。每个订阅渠道按其渠道类型对应数据源声明的最小轮询间隔被周期性查询：用渠道 OAuth 凭据调该数据源的用量接口，从响应提取所有用量窗口使用率并取最大值作为瓶颈使用率，钳制到 [0, 100] 后连同本次成功刷新的时间戳写入渠道用量缓存。

渠道用量缓存是各节点的进程内存，条目结构为「瓶颈使用率单值 + 刷新时间戳」；多节点部署下轮询产物经 Redis 快照抵达非 master 节点：master 分批遍历渠道，每处理完一批就把全部渠道条目以 JSON 全量快照写入 Redis，非 master 节点每 30 秒读取快照并整体替换本地缓存。

## 约束

- 仅 master 节点执行轮询，非 master 不发起任何上游用量请求。
- 各渠道类型的查询周期等于其数据源声明的最小轮询间隔；不同类型渠道的查询周期互不影响。
- 只轮询启用状态的订阅渠道；禁用（含手动/自动禁用）渠道不轮询，其缓存条目不再更新。
- 单个渠道查询失败（网络错误、非 2xx、响应不可解析、数据源判定无效）只记录该渠道失败，本轮继续处理其余渠道；失败渠道保留上一次成功缓存的数值与时间戳，不写入新数据。
- 瓶颈使用率缓存前钳制到 [0, 100]。
- 缓存条目的有效期语义：距最近一次成功刷新超过 10 分钟即视为过期；过期的判定由读取方执行，轮询任务不删除过期条目。
- Redis 可用时：master 写快照失败仅记录日志，本地缓存与本轮轮询结果不受影响；非 master 读快照失败或快照缺失时保留本地现有条目。过期判定始终按条目自带刷新时间戳由读取方执行，渠道选择只读本地缓存、不直接读 Redis。
- Redis 不可用时：行为与单进程内存缓存一致；非 master 节点在启动时记录一条警示日志，说明用量均衡与触顶保护在该节点不生效。

## 例子

渠道 A（Codex，数据源间隔 60 秒）、渠道 B（Claude 订阅，数据源间隔 180 秒）、渠道 C（Codex）均为启用状态。A 每 60 秒被查询一次，某次响应两窗口使用率为 42.5 与 80.1，缓存写入（瓶颈 80.1，刷新时间 now）；B 每 180 秒被查询一次；某轮 C 上游返回 500，C 保留上一次成功的缓存不变，A、B 的查询不受 C 失败影响。

## 验收

- [ ] Codex 渠道每 60 秒被查询一轮，Claude 订阅渠道每 180 秒被查询一轮；非 master 节点不发起任何用量请求。
- [ ] 禁用状态的订阅渠道不被轮询。
- [ ] 某渠道返回 500 时，其余渠道当轮仍被正常刷新，该渠道缓存保留旧值。
- [ ] 瓶颈使用率 120 的查询结果缓存后读出为 100。
- [ ] 快照 JSON 经导出→加载往返后，触顶判定与剩余比例与导出前一致，刷新时间戳保留（旧时间戳条目加载后仍判过期）。
- [ ] 非 master 读快照失败时本地缓存保留旧值。
- [ ] Redis 未启用时，非 master 节点启动日志含用量均衡不生效的警示。
- [ ] master 写快照失败时本轮轮询正常结束、本地缓存已更新。
