# 管理端渠道列表订阅用量打标

## 目的

管理员在渠道列表一眼看出订阅渠道的额度消耗程度、是否正因触顶被移出选路，以及用量数据的新旧。

## 逻辑

渠道列表页加载渠道数据后，额外拉取一次管理端订阅用量端点，按渠道 ID 把用量条目合并到订阅渠道行（订阅渠道指 type 57 Codex 与 type 61 Claude Subscription，前端用与后端对齐的类型集合常量判定）。展示分三处：

- **用量**：订阅渠道的余额列位置显示瓶颈使用率百分比与迷你进度条（订阅渠道无余额概念）。
- **触顶标**：`saturated=true` 时，状态列在「已启用」徽标旁追加红色「触顶」徽标；`saturated=false` 时无此徽标。
- **tooltip**：悬停触顶标或使用率时展示瓶颈使用率（附触顶阈值 95 说明）、最后刷新时间（绝对 + 相对）、预计下次刷新时间。预计下次刷新 = `refreshed_at` + 该渠道类型轮询周期（Codex 60 秒、Claude 订阅 180 秒），文案注明为预计值、轮询失败或渠道禁用时不会如期兑现。

## 约束

- 触顶判定只读端点返回的 `saturated` 字段，前端不得用使用率数值重算。
- 端点响应中无该渠道条目时，用量位置显示「暂无数据」，不显示触顶标与进度条。
- `refreshed_at` 距当前时间超过 10 分钟时，使用率仍显示最后已知值，并在旁边追加「已过期」徽标。
- 非订阅渠道行的全部列渲染与本功能引入前完全一致；用量端点请求失败时列表正常渲染，订阅渠道按「暂无数据」降级。
- 所有新增文案走 i18n（英文源串作 key），覆盖全部支持语言。
- 本功能不新增任何持久化字段，不改变渠道列表接口的请求与响应结构。

## 例子

列表中有四个渠道：OpenAI 渠道 A、Codex 渠道 B（端点条目：62.4，30 秒前刷新，saturated=false）、Claude 订阅渠道 C（96.2，42 秒前刷新，saturated=true）、Codex 渠道 D（端点无条目）。渲染结果：

- A 行与引入前完全一致。
- B 行余额列位置显示 62.4% 与进度条，无触顶标。
- C 行状态列为「已启用」+ 红色「触顶」，余额列位置显示 96.2%；悬停显示 tooltip：瓶颈使用率 96.2%（阈值 95）、最后刷新 42 秒前、预计下次刷新约 138 秒后（预计值说明）。
- D 行用量位置显示「暂无数据」。

## 验收

- [ ] saturated=true 的订阅渠道状态列显示「已启用」+ 红色「触顶」双徽标；saturated=false 时只有「已启用」。
- [ ] 订阅渠道余额列位置显示使用率百分比与进度条；非订阅渠道余额列渲染与引入前一致。
- [ ] tooltip 含使用率、最后刷新绝对与相对时间、预计下次刷新（Codex 按 60 秒、Claude 订阅按 180 秒推算）及预计值说明。
- [ ] 端点无条目的订阅渠道显示「暂无数据」，无触顶标。
- [ ] refreshed_at 距今 11 分钟的条目显示最后已知使用率 + 「已过期」徽标。
- [ ] 用量端点请求失败时渠道列表正常渲染，订阅渠道显示「暂无数据」。
- [ ] 新增文案在全部支持语言的 locale 文件中键集对称。
