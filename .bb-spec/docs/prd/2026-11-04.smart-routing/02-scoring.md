# 打分与选档

## 用户故事
### P0：作为员工，我希望简单问题自动用便宜的模型、难问题自动用强模型，以便既省钱又答得好

**用例（主路径）**
- 场景：auto-gpt 的打分模型是 gpt-5.6-luna，分组顺序 subscription → api；可信度门槛 0.6，简单题消息长度上限 2000 字。
- 操作：运营小张发"把这句话翻成英文"。
- 预期：打分结果是"改写或整理、想得浅、一步、出错代价低、把握 0.9"，落到简单档。
- 操作：财务小刘发"核对本月应付账款的差异，写一段结论"。
- 预期：出错代价被判为高，落到困难档。

### P0：作为员工，我希望打分出问题时也不影响我正常使用

**用例（边界 / 异常）**
- 场景：打分模型 2 秒内没有返回。
- 预期：这次请求用默认档照常回答；日志写明"打分超时"；这次打分不扣费。
- 场景：打分模型返回的内容不是规定的格式，或者某个标签的取值不在规定的选项里。
- 预期：用默认档；日志写明"打分结果格式不对"。
- 场景：小张的余额连这次打分的钱都不够。
- 预期：返回和普通请求一样的余额不足错误，不调用主请求。

## 约束
- C1：请求里的最后一条输入是用户写的文字 → 打分；最后一条输入是工具调用的结果 → 不打分，也不产生打分记录。
- C2：发给打分模型的内容只有这几样：
  - 最新一条用户消息，超过 4000 字时截断；
  - 往前再取 N 条用户消息，每条只取开头 200 字（N 是顾问设置里的"连续不满意次数"），加上最新一条共 N+1 条；
  - 本地算出的特征：最新消息的字数、对话轮数、是否带图片或文件、是否贴了代码或表格。

  不发系统提示词、工具调用结果的内容和思考内容。
- C3：打分模型必须按下面的固定选项作答，选项之外的取值一律视为格式不对：

  | 标签 | 选项 |
  |---|---|
  | 任务类型 | 闲聊或简单问答 / 查找资料或信息 / 改写或整理 / 生成或修改内容 / 分析或排查 / 规划或设计 |
  | 要想多深 | 低 / 中 / 高 |
  | 工作量 | 一步 / 几步 / 很多步 |
  | 出错代价 | 低 / 高 |
  | 工作类型 | 代码 / 财务 / 运营 / 数据分析 / 其他 |
  | 打分把握 | 0 到 1 之间的数 |
  | 用户反馈（最近每条用户消息各一个） | 满意 / 不满意 / 中性 |

  "工作类型"只写进日志，不参与选档。
- C4：选档规则按顺序匹配，命中第一条就停：
  1. 打分把握 < 可信度门槛 → 默认档；
  2. 要想多深 = 高，或出错代价 = 高，或任务类型 = 规划或设计 → 困难档；
  3. 任务类型是"闲聊或简单问答 / 查找资料或信息 / 改写或整理"之一，且要想多深 = 低，且工作量 = 一步，且最新消息字数 < 简单题消息长度上限 → 简单档；
  4. 其余 → 普通档。
- C5：打分失败（超时、上游报错、返回内容不符合 C3）→ 用默认档；日志写明失败原因。
- C6：打分模型的输出长度有固定上限（300 个 token），不受用户请求里任何参数的影响。
- C7：打分调用的分组：密钥分组是 auto 时，按打分模型配置的分组顺序尝试，并跳过用户没有权限使用的分组；密钥分组不是 auto 时，只用密钥自己的分组；找不到可用渠道就算打分失败。
- C8：打分成功拿到用量 → 按"打分模型价格 × 打分实际用到的分组倍率"扣用户额度，单独记一条消费记录，请求 ID 和主请求相同；拿不到用量（超时、报错）→ 不扣费，也没有这条消费记录。
- C9：用户余额连这次打分的钱都不够 → 返回和普通请求一样的余额不足错误，不调用打分模型，也不调用主请求。
- C10：打分提示词内置在 new-api 里，配置页没有修改它的入口。

## 验收
- [ ] C1：最后一条是用户文字的请求 → 有打分调用；最后一条是工具结果的请求 → 没有打分调用。
- [ ] C2：截获发给打分模型的内容 → 只含最新消息（5000 字的消息被截到 4000 字）、往前 N 条用户消息各开头 200 字（加最新一条共 N+1 条）和本地特征；不含系统提示词、工具结果内容和思考内容。
- [ ] C3：打分模型返回"任务类型 = 写诗"→ 按格式不对处理，用默认档。
- [ ] C4：按下表输入标签，选档结果一致：把握 0.5 → 默认档；出错代价高 → 困难档；规划或设计 → 困难档；改写或整理 + 低 + 一步 + 1500 字 → 简单档；改写或整理 + 低 + 一步 + 2500 字 → 普通档；查找资料 + 低 + 很多步 → 普通档。
- [ ] C5：打分超时 → 用默认档，日志写"打分超时"；返回内容不是规定格式 → 用默认档，日志写"打分结果格式不对"。
- [ ] C6：用户请求里把 max_tokens 设成很大的值 → 打分调用的输出上限仍是 300。
- [ ] C7：打分分组顺序为 vip → api，用户无权使用 vip → 打分走 api；密钥分组为 subscription（不是 auto）→ 打分只走 subscription。
- [ ] C8：打分成功 → 有一条模型名为打分模型的消费记录，扣费 = 打分模型价格 × 实际分组倍率，请求 ID 与主请求相同；打分超时 → 没有这条记录。
- [ ] C9：把用户余额设成小于一次打分的费用 → 返回余额不足错误，上游没有收到打分请求和主请求。
- [ ] C10：配置页和配置 JSON 里都没有打分提示词这一项。

## 验证路径
1. 准备 6 条覆盖各档的消息（翻译、查资料、写功能、核对账目、规划方案、低把握的模糊问题）依次发给 auto-gpt → 每条落到的档位和 C4 一致，日志里有对应的标签。
2. 让打分模型的渠道超时 → 请求照常由默认档回答，日志写"打分超时"，没有打分消费记录。
3. 把用户余额调到不够一次打分 → 返回余额不足。
