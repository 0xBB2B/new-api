# 会话与换档

## 用户故事
### P0：作为员工，我希望同一段对话里中途换模型时请求不报错，以便对话能一直进行下去

**用例（主路径）**
- 场景：小王在 Codex 的一段对话里，上一轮由简单档（api 分组的渠道）回答，这一轮打分落到困难档（subscription 分组的渠道）。
- 操作：小王发出这条消息。
- 预期：发往困难档渠道之前，历史里上一轮留下的加密思考内容被去掉，可读的摘要保留；上游正常返回，不报 invalid_encrypted_content。

### P0：作为管理员，我希望长对话里不要轻易换到便宜模型，以便不因重读整段历史而多花钱

**用例（主路径）**
- 场景：一段对话上一轮是困难档，这次请求的输入约 86,000 token，降档时历史 token 上限是 20,000。
- 操作：用户发"好的，谢谢"，打分落到简单档。
- 预期：仍用困难档；日志写明"对话历史 86,000 token，超过降档上限 20,000，保留上一轮的困难档"。

**用例（边界 / 异常）**
- 场景：同一轮里，客户端带着工具调用的结果接着发请求。
- 预期：不打分，沿用这一轮用户新消息选定的模型（包括顾问）。
- 场景：一段新对话的第一条请求就是工具结果（会话里没有记录）。
- 预期：用默认档。

## 约束
- C1：会话识别：请求带 prompt_cache_key → 用"密钥 + prompt_cache_key"识别会话；不带 → 用"密钥 + 第一条用户消息的内容"算出的指纹识别。同一个密钥、第一条用户消息完全相同的两段对话，会被当成同一个会话。
- C2：每个会话记下三样东西：本轮选定的模型（档位或顾问）、最近一次不是顾问的档位、上一次请求实际用的渠道。最后一次请求后 3600 秒内没有新请求，记录作废，下一条请求当作新会话处理。
- C3：会话记录只在主请求成功后更新；同一个会话的多个请求同时进行时，以最后完成的那个为准。没有配置 Redis 时，记录存在内存里，new-api 重启后全部作废。
- C4：工具结果续跑（最后一条输入是工具调用结果）→ 沿用"本轮选定的模型"；会话没有记录时用默认档。
- C5：档位从低到高依次是简单档、普通档、困难档。用户新消息选出的档位比"最近一次不是顾问的档位"高 → 直接用新档位。
- C6：选出的档位比"最近一次不是顾问的档位"低 → 本次请求的输入 token 估算值小于"降档时历史 token 上限"才换到新档位；否则保留原档位，日志写明降档被拦、打分结果是哪一档、输入 token 数。新档位不管是打分得出的还是打分失败后的默认档，都按这条处理。
- C7：会话没有记录（新会话）→ 直接用选出的档位，不做降档判断。
- C8：Responses 请求每次发往上游之前（包括重试换渠道之后），如果这次用的渠道和会话里记的上一次渠道不同，就去掉历史里的加密思考内容：思考项里的加密内容和它的 id 去掉，保留可读的摘要；没有摘要的思考项整项去掉。渠道相同时原样发送。日志记下清理了几段。Chat Completions 请求不做这项清理。

## 验收
- [ ] C1：同一个密钥、同一个 prompt_cache_key 的两次请求 → 同一个会话；两段对话都不带 prompt_cache_key、第一条用户消息不同 → 两个会话；第一条用户消息完全相同 → 同一个会话。
- [ ] C2：会话最后一次请求后过了 3601 秒再发工具结果续跑 → 按新会话处理，用默认档。
- [ ] C3：主请求失败（上游报错）→ 会话记录不变；重启未配置 Redis 的 new-api 后再发续跑请求 → 用默认档。
- [ ] C4：本轮由困难档回答，之后的 3 次工具结果续跑 → 都用困难档，且都没有打分调用。
- [ ] C5：上一轮简单档、本次打分困难档 → 用困难档。
- [ ] C6：上一轮困难档、本次打分简单档、输入 15,000 token → 用简单档；输入 86,000 token → 用困难档，日志写明降档被拦；打分失败且默认档是普通档、输入 86,000 token → 用困难档。
- [ ] C7：新会话的第一条用户消息打分为简单档 → 用简单档。
- [ ] C8：上一次渠道 A、这次渠道 B，历史里有 2 段带摘要的加密思考内容和 1 段没有摘要的 → 上游收到的请求里，加密内容和 id 都去掉了，2 段摘要还在，没有摘要的那段整段去掉，日志记"已清理 3 段"；两次都是渠道 A → 请求原样发送。

## 验证路径
1. 在 Codex 里开一段对话：先问一个简单问题，再提一个困难任务 → 第二轮换到困难档渠道，上游不报 invalid_encrypted_content，日志显示清理了思考内容。
2. 困难任务执行过程中的工具结果续跑 → 都用困难档，没有打分记录。
3. 对话历史超过 2 万 token 后发"好的" → 仍是困难档，日志写明降档被拦。
