# 虚拟模型与路由

## 用户故事
### P0：作为员工，我想在客户端里只填一个虚拟模型名，就能自动用上合适的模型，以便不用自己切模型

**用例（主路径）**
- 场景：员工小王的密钥分组是 auto，自动分组顺序是 subscription、api。管理员配置的 auto-gpt 接口为 Responses，困难档是 gpt-5.6-sol，分组顺序 subscription → api，思考力度 high。
- 操作：小王在 Codex 里把模型填成 auto-gpt 并发了一条消息，打分结果是困难档。
- 预期：new-api 用 gpt-5.6-sol 在 subscription 分组里找渠道，发往上游的思考力度是 high；Codex 收到的响应里模型名是 gpt-5.6-sol。

### P0：作为管理员，我希望路由后的扣费和直接请求真实模型一样，以便订阅分组和 API 分组的成本区分不变

**用例（主路径）**
- 场景：同上，subscription 分组倍率 0.5。
- 操作：查看这次请求的扣费。
- 预期：扣费等于"直接用 gpt-5.6-sol、在 subscription 分组请求同样内容"时的扣费。

**用例（边界 / 异常）**
- 场景：员工小李的密钥分组固定为 api（不是 auto），困难档的分组顺序是 subscription → api。
- 操作：小李请求 auto-gpt，打分结果是困难档。
- 预期：只在 api 分组里找 gpt-5.6-sol 的渠道，不去 subscription 分组。
- 场景：小李的 api 分组里没有 gpt-5.6-sol 的可用渠道。
- 预期：改用默认档的模型，仍然只在 api 分组里找；默认档的模型在 api 分组里也没有可用渠道时，返回和普通请求一样的"没有可用渠道"错误。
- 场景：困难档的分组顺序里有一个 vip 分组，小王没有权限使用 vip。
- 预期：跳过 vip，只试小王有权限的分组。
- 场景：小王用 Chat Completions 接口请求 auto-gpt。
- 预期：返回 400，错误信息写明 auto-gpt 只支持 Responses 接口；不打分、不扣费。

## 约束
- C1：请求的模型名是虚拟模型名 → 选渠道、计费、写日志都用选中档位的真实模型名；返回给客户端的响应里，模型名是真实模型名。
- C2：密钥分组是 auto → 按选中档位配置的分组顺序依次尝试；每个分组内的重试、"跨分组重试"开关都沿用密钥现有的设置。
- C3：档位的分组顺序里，用户没有权限使用的分组一律跳过；全部被跳过时，返回和普通请求一样的"没有可用渠道"错误。
- C4：密钥分组不是 auto → 只在密钥自己的分组里找选中档位的模型；该分组没有这个模型的可用渠道时，改用默认档的模型，仍只在密钥自己的分组里找；默认档也找不到时，返回"没有可用渠道"错误。
- C5：路由后的扣费，等于用同一个真实模型、在同一个分组直接请求时的扣费（含分组倍率和"用户分组对使用分组"的特殊倍率）。
- C6：选中档位配了思考力度（low / medium / high）→ 发往上游的请求用这个值，覆盖客户端传来的值；档位选的是"不覆盖"→ 保留客户端传来的值。Responses 和 Chat Completions 两种接口都按这条处理。
- C7：客户端用的接口和虚拟模型的接口不一致 → 返回 400，错误信息写明这个虚拟模型只支持哪种接口；这次请求不打分、不扣费。
- C8：令牌设了模型白名单时，白名单里有虚拟模型名就放行，不再检查档位里的真实模型；白名单里没有虚拟模型名时，和普通模型不在白名单里一样被拒绝。
- C9：模型列表接口（/v1/models）返回的列表里包含已配置的虚拟模型名；令牌设了模型白名单时，虚拟模型和普通模型一样按白名单过滤。
- C10：选中档位在可尝试的分组里，所有渠道都按现有规则重试失败后，返回错误，不自动换到别的档位。
- C11：管理员保存新的虚拟模型配置后，之后的新请求立即按新配置路由，不用重启。
- C12：用虚拟模型名请求压缩接口（`POST /v1/responses/compact`），且虚拟模型支持 Responses 接口 → 不打分，沿用这段对话当前选定的模型（会话没有记录时用默认档）；按实际用到的模型计费。
- C13：用虚拟模型名走 Responses WebSocket 长连接 → 返回明确的错误"虚拟模型只支持 HTTP 请求"，不打分、不扣费。

## 验收
- [ ] C1：auto 密钥请求 auto-gpt、打分为困难档 → 上游收到的模型名是 gpt-5.6-sol，客户端响应里的模型名是 gpt-5.6-sol，日志里的模型名是 gpt-5.6-sol。
- [ ] C2：困难档分组顺序为 subscription → api，subscription 分组下没有可用渠道 → 改用 api 分组的渠道；密钥关闭了跨分组重试时，subscription 分组的渠道失败后不换到 api。
- [ ] C3：困难档分组顺序是 vip → api，用户无权使用 vip → 只用 api 分组；分组顺序只有 vip 时 → 返回"没有可用渠道"错误。
- [ ] C4：密钥分组为 api，困难档模型在 api 分组无渠道 → 使用默认档模型的 api 渠道；默认档也无渠道 → 返回"没有可用渠道"错误。
- [ ] C5：同一段输入分别请求 auto-gpt（路由到 gpt-5.6-sol、subscription 分组）和直接请求 gpt-5.6-sol（subscription 分组）→ 两次主请求的扣费相同。
- [ ] C6：困难档思考力度为 high，客户端传 low → 上游收到 high；困难档为"不覆盖"，客户端传 low → 上游收到 low。两种接口各测一次。
- [ ] C7：Responses 虚拟模型收到 Chat Completions 请求 → 400，错误信息含虚拟模型名和 "Responses"；没有打分记录，也没有扣费记录。
- [ ] C8：白名单只有 auto-gpt → 请求 auto-gpt 成功；白名单只有 gpt-5.5 → 请求 auto-gpt 被拒绝。
- [ ] C9：/v1/models 的结果里有 auto-gpt；令牌白名单不含 auto-gpt 时，结果里没有它。
- [ ] C10：困难档所有分组的渠道都失败 → 返回错误，日志里没有改用其他档位的记录。
- [ ] C11：把困难档的模型从 gpt-5.6-sol 改成 gpt-5.5 并保存 → 下一次困难档请求使用 gpt-5.5。
- [ ] C12：会话当前为困难档时，用 auto-gpt 请求压缩接口 → 不调用打分模型，上游收到困难档模型；没有会话记录时上游收到默认档模型。
- [ ] C13：用 auto-gpt 建立 Responses WebSocket 并发起请求 → 收到"只支持 HTTP 请求"的错误，没有扣费记录。

## 验证路径
1. 配好 auto-gpt，用 auto 密钥通过 Responses 接口请求，并让打分落到困难档 → 检查上游收到的模型名、思考力度，以及响应和日志里的模型名。
2. 停用 subscription 分组的渠道再请求 → 改走 api 分组；把密钥换成分组固定为 api 的密钥 → 只走 api 分组。
3. 用 Chat Completions 接口请求 auto-gpt → 400，没有任何扣费记录。
4. 对比路由请求和直接请求真实模型的扣费 → 相同。
