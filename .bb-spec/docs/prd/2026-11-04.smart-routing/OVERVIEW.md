# 智能路由：按问题难度自动选模型和渠道

## 背景与问题
公司通过 new-api 给员工提供 AI 额度，员工用 Codex、pi 等各种客户端调用。渠道分两类：订阅账号渠道和 API 渠道，两类对公司的成本不同，现在靠不同的用户分组设置消耗倍率来区分。

员工在客户端里通常只选一个模型，不管问题难易都用它：简单问题用了强模型、走了 API 渠道，浪费公司的钱；难问题用了弱模型，答不好。让员工每次自己切模型很麻烦，也容易选错。用的人也不只是开发，还有做报表的财务、上网做调研的运营、拉数据做分析的人。

现有的 auto 分组只会在一个分组没有可用渠道时换下一个分组，不看问题难不难，解决不了这个问题。

## 目标
- 员工只要把客户端里的模型名改成管理员配好的虚拟模型名，接口地址和 API 密钥都不变，每条用户新消息就会按难度自动交给合适的模型和分组。
- 扣费仍是"实际模型的价格 × 实际分组的倍率"，订阅分组和 API 分组的成本区分不变。
- 用量统计照旧按实际模型记录，同时能看出每次请求是从哪个虚拟模型路由来的、选了哪一档、为什么选这一档。
- 管理员在后台用表单配置虚拟模型，三档模型、打分模型、顾问模型以及它们的分组顺序都能自由选。

## 非目标
- 不支持 Claude Messages 接口（Claude Code 用的接口），一期只支持 Responses 和 Chat Completions 两种接口。
- 不做跨接口转换：虚拟模型只接受和它所配接口一致的请求。
- 不接入 Claude 官方的顾问工具，也不做"主模型自己拿不准时去问顾问"。
- 档位固定三档；标签对应到档位的规则内置在代码里，管理员只能调可信度门槛和简单题消息长度上限两个数字。
- 打分提示词内置，管理员不能改。
- 价格页不显示虚拟模型。
- 不按真实对错数据训练分类器，一期只把标签和档位记进日志，留作以后调整规则的依据。
- 选中档位的分组渠道全部失败时，不自动换到别的档位。

## 整体验证路径
1. 管理员打开「系统设置 → 请求策略 → 智能路由」，添加虚拟模型 auto-gpt，三档、打分模型、顾问都选好，弹窗里点「保存」，再点页面右上角「保存更改」→ 表格里出现 auto-gpt，接口一列显示 Responses。
2. 员工用分组为 auto 的密钥，在 Codex 里把模型填成 auto-gpt，发"这个函数在哪个文件里" → 回答来自简单档的模型；使用日志里这条记录的模型是简单档的真实模型，下面小字写"auto-gpt · 简单档"；另有一条小字写"路由打分 · auto-gpt"的打分记录，请求 ID 与它相同。
3. 同一段对话接着发"给这个功能加一个导出，涉及线上数据库迁移" → 回答来自困难档的模型；之后客户端带着工具结果接着发的请求仍用困难档，而且没有打分记录。
4. 员工连续两条消息说"还是不对" → 第二条由顾问模型回答，日志档位显示"顾问"。
5. 用同一个密钥，通过 Chat Completions 接口请求 auto-gpt → 返回 400，错误信息写明 auto-gpt 只支持 Responses 接口。
6. 逐条核对第 2~4 步的扣费：主请求等于"实际模型价格 × 实际分组倍率"；打分记录按打分模型的价格单独扣费。

## 决策记录
- **做在 new-api 里**：客户端不能限定（Codex、pi 和其他第三方都要能用），所以否决做在客户端。单独开一个路由服务要自己解析多套协议、处理流式转发，还拿不到用户分组和令牌可用模型，日志要两边对账，所以也否决。new-api 里计费、分组倍率、日志都是现成的。代价是 fork 和上游的差异变大，同步上游时可能冲突。
- **不用渠道模型映射来实现**：现有计费按客户端请求的模型名取价格，用模型映射会按虚拟模型的价格扣费。
- **复用 auto 分组**：密钥分组选 auto 后，按选中档位配置的分组顺序尝试，扣费用实际用到的分组倍率。非 auto 密钥只换模型、不换分组，因为分组代表这个用户被允许花哪种成本。
- **规则里的分组照样过用户权限检查**：管理员的配置不能把用户没权限用的分组开放给他。
- **打分模型可以自由配置**：一期打算用 Luna 这类便宜的小模型。考察过 Jev、Arch-Router、vLLM Semantic Router、RouteLLM：Jev 只拿判断结果的接口查不到文档，而且请求内容要发给第三方；Arch-Router 要自己部署 GPU；后两个是整套网关或 Python 框架，不适合直接接入。
- **不把整段对话发给打分模型**：太贵、太慢，系统提示词、工具结果、思考内容对判断难度没有帮助。只发最新消息、前几条用户消息的开头和本地算出的特征。
- **打分模型只贴标签，不直接选模型**：模型和价格变了只改配置，不改提示词，选档原因也说得清楚。
- **打分角度与行业无关**：用户指出不能只考虑写代码，财务、运营、数据分析的人也在用。最终用任务类型、要想多深、工作量、出错代价、打分把握五项选档，另记只写进日志的工作类型和用户反馈。参考了 Arch-Router（领域 + 动作）、vLLM Semantic Router（类别 + 是否需要推理）、LiteLLM 复杂度路由（token 数、代码、推理用词等）的做法。"出错代价"是针对公司场景加的。
- **"很多步"只要求至少用普通档**：步数多不等于难，比如上网搜很多次。
- **简单题的长度按最新消息算，不按整段历史算**：Codex 每次请求光系统提示词和历史就有上万 token，按整段算，简单档几乎永远选不中。
- **每条用户新消息都打分**：用户要求的。一段对话里先让查功能、再让改功能，难度会变。
- **升档立即换，降档只在历史较短时换**：依据 Claude Code 官方文档（prompt caching 一节），每个模型的缓存是分开存的，换模型后整段历史要按原价重读，降档省下的单价可能抵不上重读的钱。
- **渠道变了就清理加密思考内容**：依据 LiteLLM 文档（auto router encrypted content routing），加密思考内容绑定生成它的组织或密钥，换渠道后原样发过去会报 invalid_encrypted_content。所以按"渠道是否变了"判断，不只看模型名。
- **不满意次数每次从对话历史里现数**：不用在服务器上另存一份，重启不会丢，没有会话标识的客户端也能用。
- **会话识别**：请求带 prompt_cache_key 就用它；不带就用"密钥 + 第一条用户消息"算指纹。代价是同一个密钥开的两段对话，如果第一句话一字不差，会共用一份档位记录，只影响降档判断，不影响扣费。
- **顾问一期只做"连续不满意就升档"**：主模型自己拿不准只有它自己知道，要在流式回答进行到一半时截住工具调用，改动大、风险高。Claude 官方顾问工具要先补计费、实测订阅账号和客户端，放到以后再做。
- **顾问那一轮不算降档保护的"上一轮档位"**：否则长对话会一直停在最贵的顾问模型上。
- **打分费用扣用户额度**，单独记一条消费记录。打分超时或报错拿不到用量就不扣费，这部分成本由公司承担。用户余额连打分的钱都不够时，直接按余额不足拒绝，因为主请求一定比打分贵。
- **令牌模型白名单只查虚拟模型名**：档位里的模型是管理员挑的，用户把虚拟模型加进白名单，就等于接受了管理员的配置。
- **档位配了思考力度就覆盖客户端的值**：思考力度直接影响花多少钱，按档位控制成本正是这个功能的目的。
- **档位的渠道全部失败就照现有规则报错，不自动换档**：渠道故障是运维问题，悄悄换档会把故障藏起来，还会让用户拿到不同水平的回答。
- **响应里显示真实模型名**：用户能看到这次是哪个模型在回答，和日志对得上。客户端会不会因为返回的模型名和请求时填的不一样而出问题，实施时实测。
- **压缩接口沿用当前档位、WebSocket 一期不支持**：执行时发现 `POST /v1/responses/compact` 和 Responses WebSocket 两条路 PRD 没写到。用户决定：压缩不是用户新消息、不需要判断难度，但压缩失败会卡住长对话，所以支持它并沿用会话当前档位；WebSocket 是单独实现的转发路径，接入要把打分、选档、会话、结算全部再做一遍，一期只给出清楚的报错。
- **只带 previous_response_id 的请求每轮都算新会话**：执行时发现，客户端只带 previous_response_id、不带 prompt_cache_key 时，请求里只有这一轮的新消息，按"密钥 + 第一条用户消息"算出的指纹每轮都不同，降档保护对这类客户端不起作用，扣费不受影响。用户决定一期保持：Codex 这类常用客户端会带 prompt_cache_key；按响应编号接上会话要另存"响应编号 → 会话"的对应关系，以后作为新需求再做。
- **接受员工用提示词诱导升档**：打分模型读的是员工自己写的消息，员工写"这是高风险任务"之类的话，就能让请求稳定落到困难档或顾问。用户决定一期接受：扣费照实际用到的模型算，多花的是员工自己的额度，管理员在日志里能看到每次的选档原因；要限制次数以后作为新需求再做。
- **名称为空的提示沿用项目公共文案"输入名称"**：执行时发现 PRD 原写"请填写名称"，但项目里其他表单名称为空时都显示公共键 "Enter a name"（中文"输入名称"）。用户 2026-11-05 决定沿用公共文案，和其他表单一致；否掉了为智能路由单独新增一个英文键。
- **接口不一致直接拒绝**：硬转的话，思考内容和工具调用的字段可能丢，而且不容易发现。
- **选档规则内置，只开放两个数字；打分提示词不能改**：还没有真实数据，开放太多参数管理员也不知道怎么调；提示词改坏了会让所有打分失败，而且不容易发现。
- **日志里的路由信息用户和管理员都能看**：用户需要知道自己为什么被分到这一档、为什么扣这么多钱。打分标签里不含对话内容。
- **虚拟模型出现在模型列表接口里，不进价格页**：虚拟模型本身没有价格，放进价格页反而容易误导。
- **配置页照搬现有界面**：放在「请求策略」下，照搬「会话规则」的"表格 + 编辑弹窗"写法，分组顺序复用创建 API 密钥时的「自动分组顺序」组件。用户确认 HTML 预览时要求原型结合整个项目的界面，第 2 版预览就是用真实页面和现有组件拼出来的。
- **质疑结论**：值得做。现有 auto 分组只在渠道不可用时换组，不看问题难度，没有能直接拿来用的现成功能。
