# 打分模型的思考力度

## 背景与问题
管理员给虚拟模型配的打分模型是 deepseek-v4.1-flash，这个模型默认先思考再作答。打分调用的输出上限固定为 300 个 token，思考内容先把这 300 个 token 用光，返回的标签 JSON 被截断。结果每次打分都按"格式不对"处理，请求全部落到默认档，智能路由实际上没有在工作。2026-11-09 的使用日志里，4 次打分的输出都正好是 300 个 token，对应的 4 条主请求都标着「打分失败」。

打分设置里没有控制思考的地方，管理员只能换一个不思考的打分模型，或者去渠道的参数覆盖里按各家厂商的写法手动关思考。格式不对时，服务器也不记录模型到底返回了什么，排查只能靠猜。

## 目标
- 管理员能给打分模型选一档思考力度，或者留空交给模型自己决定。
- 打分调用的输出长度不再被固定上限截断。
- 不在内置能力表里的打分模型，管理员也能在「模型思考能力」里补上它支持的档位（包括 none）。
- 打分结果格式不对时，服务器日志里能看到模型的原始返回。

## 非目标
- 打分的思考力度只有"留空 / 选一档"两种，不做档位那样的"不覆盖 / 固定 / 跟随打分"三种方式。
- 不给顾问加思考力度设置；「模型思考能力」表仍然不列顾问模型。
- OpenAI 兼容渠道上，none 按标准的思考力度字段发给上游；上游要用别的字段才能关思考时，由管理员在渠道参数覆盖里处理，new-api 不为各家兼容服务单独适配。
- 打分输出不另设可配置的长度上限，耗时只由打分超时控制。
- 使用日志里不新增打分思考力度的展示。
- 打分标签、选档规则、打分计费方式不改。

## 整体验证路径
1. 管理员打开「系统设置 → 请求策略 → 智能路由」，「模型思考能力」表里出现打分模型 deepseek-v4.1-flash，来源「未确认」→ 点「覆盖」，勾上 none、low、high、max，保存。
2. 编辑 auto-gpt，在「打分」页签把思考力度选成 none，保存，再点「保存更改」→ 左栏「打分」页签的小字写「deepseek-v4.1-flash · none」。
3. 员工用 auto-gpt 发一条新消息 → 上游收到的打分请求里思考力度是 none，没有输出长度上限；这条打分的消费记录里输出 token 远小于 300；主请求不再标「打分失败」，按打分结果选档。
4. 把打分思考力度改回留空 → 上游收到的打分请求里没有任何思考参数。
5. 让打分模型返回一段不是 JSON 的文字 → 主请求用默认档、标「打分失败」；服务器日志里有一条警告，写着虚拟模型名、打分模型名和原始返回的前 500 个字。

## 决策记录
- **问题根源是思考把输出额度用光，不是额度本身太小**：2026-11-09 的日志里 4 次打分输出都正好 300 个 token，返回很快（3 秒、100 t/s），说明是写满上限被截断。只取消上限属于缓解症状，思考模型会想得更久，变慢甚至超时；所以同时给打分加上思考力度设置，让管理员能把思考关掉或调低。
- **取消 300 token 上限**：用户 2026-11-09 决定。推翻了 `2026-11-04.smart-routing` 中 02-scoring 的 C6（"打分输出长度固定上限 300 个 token"）。代价是打分费用和耗时不再有固定上限：耗时由打分超时（`timeout_ms`，100～30000 毫秒）兜住，超时不扣用户费用；预扣费只看输入 token，不受影响，结算按实际用量。被否决的做法：把上限改成可配置、默认 300（多一个配置项，管理员关掉思考后 300 已经够用，没被选用）。
- **打分思考力度开放配置**：用户 2026-11-09 决定。推翻了 `2026-11-05.smart-routing-effort` 非目标里的"打分模型的思考力度不开放配置"。当初的考虑是打分只需要快和便宜，但打分模型默认会思考时，不让管理员控制就会像这次一样全部失败。
- **只做"留空 / 选一档"**：打分本身没有打分结果可以跟随，「跟随打分」没有意义；「不覆盖」对打分也没有对象（打分请求不是客户端发的），留空就是交给模型默认。
- **下拉只列能力表里这个模型支持的档位**：用户 2026-11-09 选定，和档位的力度下拉一致，避免选出上游会报错的值。被否决的做法：固定列七档、发出前再换档（能选到模型不支持的档位，界面显示的和实际发的不一致）。
- **留空时不发思考参数，并去掉 Codex 渠道写死的 low**：用户 2026-11-09 选定。思考力度只由这个设置决定，没有藏起来的特例。代价是：已有配置用 Codex 渠道打分的，会从 low 变成模型默认（一般更高），需要的话管理员自己选 low。被否决的做法：留空时保留 Codex 发 low（同一个设置在不同渠道上效果不一样）。
- **能力表也列打分模型**：用户 2026-11-09 选定。推翻了 `2026-11-05.smart-routing-effort` 中 02-thinking-capability 的 C5 里"打分模型不列"这一半。不列的话，内置表里没有的打分模型（如 deepseek-v4.1-flash）永远只能选 low / medium / high，选不到 none，关不掉思考。顾问模型仍不列，因为顾问没有思考力度设置。
- **格式不对时只写服务器日志，不进使用日志**：原始返回可能带着用户消息的片段，只给能看服务器日志的运维看；截到前 500 个字，够判断是被截断、是思考内容还是答非所问。
- **页签小字加上思考力度**：用户 2026-11-09 在原型确认时提出，和档位页签小字的写法保持一致。
