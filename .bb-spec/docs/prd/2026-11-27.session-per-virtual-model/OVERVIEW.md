# 会话按虚拟模型区分

## 背景与问题
智能路由为每段对话存一条会话记录，记着本轮选定的档位（含顾问）、最近一次不是顾问的档位，以及本轮的思考力度。三处地方会用到这条记录：
- 工具结果续跑时，沿用档位和力度；
- 用户新消息做降档保护时，拿它和新打分的档位比较。

现在用来认会话的只有两样东西：一是密钥，没有密钥的演练场请求用用户；二是 prompt_cache_key，不带时用第一条用户消息。虚拟模型不在里面。

用户在 Claude Code 里用 `/model`、在 Codex 里切模型，在同一段对话里从虚拟模型 A 换到虚拟模型 B 时，B 会读到 A 留下的记录，带来三种结果：
- 长对话换到 B 后，B 的打分落到简单档，却按 A 的困难档被降档保护拦住，多花钱；
- 换完后紧接着的工具结果续跑，走 A 上一轮的档位名，沿用 A 定下的力度，不按 B 的设置；
- 管理员给 B 设的默认档和力度方式在这几种请求上不起作用。

请求本身不会失败。这个问题是读代码时发现的，测试服日志里还没有找到实际案例。

## 目标
- 同一段对话换到另一个虚拟模型后，新虚拟模型按「新会话」处理：用户新消息不做降档保护，工具结果续跑用它自己的默认档。
- 每个虚拟模型的会话记录互不影响：在 3600 秒内从 B 切回 A，A 接着用自己原来的记录。

## 非目标
- 改会话记录里存的内容（档位、最近一次不是顾问的档位、力度），以及记录作废的时长（3600 秒）。
- 改「同一个密钥、第一条用户消息完全相同的两段对话被当成同一个会话」这一条。
- 只带 previous_response_id 的客户端每轮被当成新会话的问题。
- 压缩接口（`/v1/responses/compact`）是否改写思考力度。
- 换渠道时清理加密思考内容：它按每条思考记录上的渠道标记判断，不读会话记录。

单一子需求，无依赖。

## 整体验证路径
1. 配两个虚拟模型：A 的降档时历史 token 上限是 20,000；B 的默认档是普通档，三个档位都是「不覆盖」。
2. 用同一个密钥，在 A 上开一段对话，先提一个困难任务，再把对话聊到 86,000 token。
3. 同一段对话切到 B（第一条用户消息不变），发「好的，谢谢」，打分为简单档 → B 用简单档，日志里没有「降档被拦」。
4. 紧接着发一条工具结果续跑 → B 用简单档（本轮由用户新消息选定）。
5. 在 3600 秒内切回 A，发一条工具结果续跑 → A 用困难档（A 自己的记录还在）。

## 决策记录
- **质疑结论**：用户在同一段对话里换虚拟模型时，Claude Code（Anthropic 请求不带 prompt_cache_key，按第一条用户消息认会话）和 Codex（带 prompt_cache_key）都会被认成同一个会话。结果是降档保护按旧模型的档位拦，续跑沿用旧模型的档位和力度，导致多花钱、新模型的设置不起作用。改动只涉及认会话的方式。目前没有日志实例，用户确认值得做（2026-11-27）。
- **按虚拟模型区分的方式**：选「认会话时加上虚拟模型名」，每个虚拟模型各存一份记录。理由有两条：问题就是认会话时少了虚拟模型，补上它就从根上解决；在 3600 秒内切回原来的模型时，那个模型的上游缓存可能还在，原来的记录和降档保护仍然有意义。否决的做法是「认会话的方式不变，记录里标明是哪个虚拟模型写的，不是当前模型的就当没有并覆盖」：切回原来的模型时要从头开始，而且多一次判断。用户 2026-11-27 定。
- **用路由里配置的名字**：认会话用的是虚拟模型在路由配置里的名字，不是客户端请求里写的原样。管理员改了虚拟模型的名字后，对话按新名字从新会话开始，旧名字下的记录 3600 秒后作废。
- **换模型后按新会话处理**：沿用已合并 PRD `2026-11-04.smart-routing` 会话与换档的规则。会话没有记录时，工具结果续跑用默认档，用户新消息不做降档保护。用户 2026-11-27 确认。
- **升级时现有会话作废一次**：认会话的方式变了，升级那一刻所有进行中的会话记录都对不上。每段对话的下一条请求按新会话处理：续跑用默认档，用户新消息不做降档保护，最多影响一轮。用户 2026-11-27 接受，不做旧记录的迁移。
- **取代已合并的会话识别规则**：已合并 PRD `2026-11-04.smart-routing` 03 的 C1 写的是「密钥 + prompt_cache_key」「密钥 + 第一条用户消息」，当时的决策记录只考虑了两段对话第一句话相同时会误合并，没考虑换虚拟模型。本 PRD 在两种识别方式里都加上虚拟模型。
