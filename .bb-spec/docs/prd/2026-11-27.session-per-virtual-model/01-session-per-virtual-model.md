# 会话按虚拟模型区分

## 用户故事
### P0：作为在一段对话里换虚拟模型的员工，我希望新虚拟模型按它自己的设置选档和定力度，以便不因旧模型的记录多花钱

**用例（主路径）**
- 场景：小王用 Claude Code 在虚拟模型 auto-gpt 上聊了很久，上一轮是困难档，这次请求的输入约 86,000 token。虚拟模型 auto-claude 的降档时历史 token 上限是 20,000。
- 操作：小王用 `/model` 切到 auto-claude，发「好的，谢谢」，打分落到简单档。
- 预期：auto-claude 用简单档，日志里没有「降档被拦」。

**用例（边界 / 异常）**
- 场景：auto-gpt 上一轮是困难档、力度是 high。小王切到 auto-claude 后，客户端紧接着发了一条工具结果续跑。auto-claude 的默认档是普通档，普通档的力度是「固定 low」。
- 预期：auto-claude 用普通档，上游收到的力度是 low。
- 场景：小王在 3600 秒内又切回 auto-gpt，客户端发了一条工具结果续跑。
- 预期：auto-gpt 用困难档，力度是 high，沿用 auto-gpt 自己的记录。

## 约束
- C1：认会话时，在原来的识别方式里加上虚拟模型：
  - 请求带 prompt_cache_key：用「密钥 + 虚拟模型 + prompt_cache_key」认；
  - 不带 prompt_cache_key：用「密钥 + 虚拟模型 + 第一条用户消息的内容」认；
  - 没有密钥的演练场请求：把「密钥」换成「用户」。

  虚拟模型取路由配置里的名字。同一个密钥、同一个虚拟模型、对话标识相同 → 同一个会话；虚拟模型不同 → 不同会话。
- C2：同一段对话换到另一个虚拟模型后，新虚拟模型没有会话记录时，按新会话处理：
  - 用户新消息直接用打分选出的档位，不做降档保护；
  - 工具结果续跑用新虚拟模型的默认档，力度按默认档自己的设置算，不沿用前一个虚拟模型的力度。
- C3：每个虚拟模型的会话记录各自更新、各自作废（最后一次请求后 3600 秒）。在 B 上的请求不改 A 的记录；在 A 的记录作废之前切回 A，A 的工具结果续跑沿用 A 记录里的档位和力度，用户新消息按 A 记录里最近一次不是顾问的档位做降档保护。
- C4：只用一个虚拟模型的对话，选档、降档保护和续跑沿用的行为和改动前完全一样。

## 验收
- [ ] C1：
  - 同一个密钥、同一个 prompt_cache_key，分别请求 A 和 B → 两个会话；
  - 两次都请求 A → 同一个会话；
  - 不带 prompt_cache_key、第一条用户消息相同，分别请求 A 和 B → 两个会话；
  - 演练场同一个用户、第一条用户消息相同，分别请求 A 和 B → 两个会话。
- [ ] C2：
  - A 上一轮是困难档；同一段对话切到 B（降档时历史 token 上限 20,000），输入 86,000 token，打分简单档 → 用简单档，没有降档被拦。
  - A 上一轮是困难档、力度 high；切到 B 后先发工具结果续跑，B 的默认档是普通档、普通档固定 low → 用普通档，力度 low。
- [ ] C3：A 上一轮是困难档、力度 high；在 B 上请求一轮简单档；3600 秒内切回 A 发工具结果续跑 → 用困难档，力度 high。切回 A 发用户新消息，输入 86,000 token，打分简单档 → 保留困难档，日志写明降档被拦。
- [ ] C4：只用 A：上一轮困难档、输入 86,000 token、打分简单档 → 保留困难档，降档被拦；之后的工具结果续跑 → 用困难档，沿用这一轮的力度。

## 验证路径
1. 配两个虚拟模型 A、B：B 的默认档是普通档，B 的普通档力度「固定 low」，降档时历史 token 上限都是 20,000。
2. 用同一个密钥在 A 上开一段对话，提一个困难任务（A 选困难档），再聊到输入超过 20,000 token。
3. 同一段对话切到 B，先让客户端发一条工具结果续跑 → 消费日志显示 B 用普通档，力度 low。
4. 在 B 上发「好的，谢谢」，打分简单档 → B 用简单档，没有降档被拦。
5. 切回 A 发一条工具结果续跑 → A 用困难档。
