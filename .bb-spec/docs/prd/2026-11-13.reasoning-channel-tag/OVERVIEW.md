# 思考记录按生成它的渠道决定去留

## 背景与问题
员工用 Codex 通过中台写代码时，会在同一段对话里切换模型：手动从 deepseek 切到 auto，或者 auto 自己在不同档位之间换渠道。Codex 每次请求都把整段历史带上，历史里有上一个模型留下的思考记录。

中台现在只在一种情况下清理思考记录：智能路由的会话记录还在，而且这次的渠道和会话里记的上一次渠道不同。会话记录只保存 1 小时，而且只有 auto 请求会更新它。2026-11-13，测试中台上出现了这种情况：员工先手动用 deepseek 聊了几轮，两个多小时后改用 auto。会话记录早已过期，中台把 deepseek 的思考记录原样转给了 GPT 渠道。上游返回 400 `Invalid 'input[16].id': 'msg_f836e1c0-…'. Expected an ID that begins with 'rs'`，这段对话之后每一轮都报错，只能新开对话。

另外，中台把 Codex 的请求转成聊天格式时，会把思考记录当成一条用户消息发出去。GPT 的思考记录会变成空的用户消息，deepseek 的会带上上游不认识的内容。

## 目标
- 同一段对话里不管怎么切模型、隔多久再继续，都不会因为别的渠道留下的思考记录而报错。
- 同一渠道连续对话时，思考记录原样发回，不丢上下文。

## 非目标
- 同一渠道内换模型（例如 gpt-6-luna 换 gpt-6.1-sol）是否需要清理：不清理，和现在一样。
- Chat Completions 格式和 Gemini 格式客户端发来的历史：这两种格式不做清理，和现在一样。
- Responses 的 compaction 条目、`previous_response_id` 这类存在上游服务器上的状态：不处理。
- 非 auto 请求的清理段数在使用日志界面上的展示：只记服务器日志，界面上不新增内容。
- 转成 Claude 格式、Gemini 格式发往上游时怎么处理思考记录：不改，现在就是跳过。

## 子需求清单
| 序号 | 子需求 | 解决的子问题 | 优先级 |
|---|---|---|---|
| 01 | [01-channel-tag](01-channel-tag.md) | 中台返回的每条思考记录都带上加密的渠道标记，下次请求能认出它来自哪个渠道 | P0 |
| 02 | [02-strip-by-tag](02-strip-by-tag.md) | 发往上游前按标记只保留这次渠道生成的思考记录，其余清理，适用所有请求 | P0 |
| 03 | [03-chat-reasoning](03-chat-reasoning.md) | 转成聊天格式时，保留下来的思考记录放进 assistant 消息的 reasoning_content，不转成用户消息 | P0 |

## 依赖与交付顺序
01 → 02；03 可与 01 并行，验收时依赖 02 的保留规则。

## 整体验证路径
1. 在 Codex 里开一段对话，先手动选 deepseek 模型聊两轮（含一次工具调用），再手动改成 GPT 模型发一条 → GPT 正常回答，不报 400；服务器日志记下清理了 deepseek 的思考记录。
2. 在同一段对话里切回 deepseek，提一个新问题并让它做带工具调用的任务 → deepseek 正常回答；GPT 那轮的思考记录被清理，deepseek 自己之前的思考记录原样发回。
3. 用 auto 在同一段对话里让请求先落到渠道 A、再落到渠道 B → 渠道 B 收到的请求里没有渠道 A 的原始思考编号和加密内容；使用日志详情的「智能路由」一块显示"上一轮用的渠道不同，已清理 X 段"。
4. 用 Claude Code 通过 auto 在两个 Claude 渠道之间切换 → 不报签名错误；同一渠道连续工具调用时思考块原样发回。

## 决策记录
- **2026-11-13，用户定：思考记录只发回给生成它的渠道。** 否掉了"一换模型就全删"：DeepSeek 带工具调用时缺了自己之前的思考会报 400（DeepSeek 思考模式文档），Claude 在工具调用过程中也要原样传回带签名的思考块（Anthropic extended thinking 文档）。
- **2026-11-13，用户定：在思考记录编号里打标记，不靠会话记录、不靠中台记账、不只看编号形状。**
  - 会话记录：只存 1 小时，只有 auto 请求更新它，今天的事故就是它漏掉的。
  - 中台记账：要存数据、要定保存期限，期限一到就重现"过期漏掉"。
  - 只看编号形状：本机 Codex 记录里 deepseek 和 glm 的编号都是 `msg_<uuid>`，分不开；GPT 换账号也分不出。
  - 打标记不用存任何数据，代价是返回给客户端的编号要改写。标记靠中台的固定密钥（`CRYPTO_SECRET` 或 `SESSION_SECRET`）加密，部署时没配这两项的话，每次重启密钥都会变，之前的标记全部读不出、全部按"没有标记"清理。所以上线前要确认部署配了固定密钥，多节点部署时各节点要用同一把。
- **2026-11-13，用户定：同一渠道才保留，不按"厂商"判断。** 中台没有可靠的厂商字段，deepseek 渠道的类型可能就是 openai。按渠道判断沿用了原 C8 的清理方式，只是"上一次渠道"改成从每条思考记录自己的标记读出。代价是同一家配了多个渠道时，在这些渠道之间切换也会清理。
- **2026-11-13，用户定：没有标记或标记解不开的，一律当作渠道不同清理。** 否掉了按编号形状猜（`rs_` 只给 GPT 类渠道）：猜错仍会 400。代价是改版前的老对话继续时，上一轮的思考过程丢一次。
- **2026-11-13，用户定：标记加密。** 渠道编号是后台内部信息，明文写进标记会让员工看出请求落在哪个渠道，也能伪造标记。
- **2026-11-13，用户定：按标记清理适用于所有 Responses 和 Claude 格式请求**，不管走不走 auto、开不开透传、走 HTTP 还是 WebSocket。只用在 auto 请求的话，"先 deepseek 再手动切 GPT"仍会 400。
- **2026-11-13，用户定：Claude 格式一起改。** 它和 Responses 格式用的是同一套会话判断，会话过期后切渠道同样会漏清理。
- **2026-11-13，用户定：转聊天格式时，保留下来的思考记录放进 reasoning_content。** 否掉了"一律丢掉"：走聊天格式的 DeepSeek 渠道带工具调用时会 400。能保留下来的思考记录一定是这个渠道自己生成的，所以它认得 reasoning_content。
- **待验证（2026-11-13 记）：GPT 发起过工具调用、再切回开着思考的 DeepSeek 时，DeepSeek 会不会因为 GPT 那几轮的 assistant 消息没有它自己的思考内容而 400。** DeepSeek 文档要求带工具时传回之前各轮的思考内容，但查到的文档片段对"别家生成的那几轮"没有说法。本需求不补造思考内容；实测会 400 的话另开需求。
- **待验证（2026-11-13 记）：标记过的编号能经过 ModelBridge 和 Codex 原样带回来。** 请求方向已有证据：上游报错里的编号 `msg_f836e1c0-…` 和 Codex 本地记录一致。响应方向只有间接证据：ModelBridge 程序里没有生成 `msg_` 编号的字符串，它的 `relay-reasoning-ids.json` 记的是收到的编号原值。实施后按整体验证路径第 1 步实测确认。
- **否掉了在 Codex 或 ModelBridge 客户端那边删思考记录**：auto 由中台挑渠道，客户端发请求时不知道这次会落到哪一家，只能缓解。
- 本需求修订已合并需求 `2026-11-04.smart-routing` 里"换渠道时清理加密思考内容"的规定：判断依据从"会话里记的上一次渠道"改为"每条思考记录自己的标记"，适用范围从智能路由扩大到所有请求。清理方式（去编号和加密内容、保留摘要，没有摘要整条去掉）不变。
