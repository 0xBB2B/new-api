# 转聊天格式时的思考记录

## 用户故事
### P0：作为员工，我希望走聊天格式的渠道也能带着自己之前的思考继续工具调用，以便 DeepSeek 这类模型不因缺思考内容报错

**用例（主路径）**
- 场景：员工小李用 Codex 请求一个只支持聊天格式的 deepseek 渠道（4 号渠道），上一轮 deepseek 思考后发起了一次工具调用。历史依次是：用户提问、一条标记为 4 号渠道的思考记录（正文"先看看目录结构"）、一次工具调用、工具结果。
- 操作：Codex 把工具结果发回中台继续。
- 预期：4 号渠道收到的聊天格式请求依次是：用户消息、一条 assistant 消息（`tool_calls` 是那次工具调用，`reasoning_content` 是"先看看目录结构"）、工具结果消息。没有空的用户消息，也没有内容是思考记录的用户消息。

**用例（异常：只有加密内容）**
- 场景：同一渠道生成的一条思考记录只有加密内容，没有摘要也没有正文。
- 操作：请求转成聊天格式。
- 预期：这条思考记录不出现在上游请求里，也不产生任何消息。

## 约束
- C1：Responses 请求转成聊天格式时，`type` 为 `reasoning` 的条目一律不转成用户消息或其他角色的消息。
- C2：标记读得出、而且标记里的渠道就是这次渠道的思考记录，取出可读文字：有正文（`content` 里的思考文字）用正文，没有正文用摘要（`summary` 里的文字）。可读文字放进它后面紧挨着的那条 assistant 消息的 `reasoning_content`。这条 assistant 消息可以是普通回答，也可以是工具调用。
- C3：连续几条思考记录对应同一条 assistant 消息时，可读文字按原顺序首尾相接，中间空一行。
- C4：思考记录后面在下一条用户消息或工具结果之前没有 assistant 消息，或者它没有可读文字（只有加密内容）→ 丢掉，不产生任何消息。
- C5：标记里的渠道不是这次的渠道、没有标记、或标记读不出来的思考记录，整条丢掉，摘要和正文都不进 `reasoning_content`。

## 验收
- [ ] C1/C2：用例里的历史转换后 → 上游请求依次是 user、assistant（tool_calls + reasoning_content "先看看目录结构"）、tool，共 3 条消息。
- [ ] C2：思考记录同时有正文"A"和摘要"B" → reasoning_content 是"A"；只有摘要"B" → reasoning_content 是"B"。
- [ ] C3：两条思考记录（正文"A"、"B"）后面接一条 assistant 回答 → 该 assistant 消息的 reasoning_content 是"A\n\nB"。
- [ ] C4：思考记录后面直接是用户消息 → 上游请求里没有对应这条思考记录的任何消息；只有加密内容的思考记录 → 同样没有。
- [ ] C5：标记为别的渠道、带摘要"S"的思考记录，没有标记、带正文"T"的思考记录，发往 4 号渠道 → 上游请求里任何消息的 reasoning_content 都不含"S"和"T"。

## 验证路径
1. 配一个只支持聊天格式的 deepseek 渠道，用 Codex 让它做一个需要两次以上工具调用的任务 → 全程不报 400；抓到的上游请求里，前几轮的思考文字在对应 assistant 消息的 reasoning_content 里，没有空的用户消息。
