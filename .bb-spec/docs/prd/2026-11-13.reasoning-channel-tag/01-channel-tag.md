# 思考记录带渠道标记

## 用户故事
### P0：作为员工，我希望中台返回的思考记录记得自己来自哪个渠道，以便之后切模型时中台能认出它

**用例（主路径）**
- 场景：员工小李在 Codex 里用 deepseek 模型提问，请求落在 5 号渠道，上游返回一条编号为 `msg_f836e1c0-0b4b-47c7-b1f0-3f05f59b2880` 的思考记录。
- 操作：小李收到回答，Codex 把这条思考记录存进对话历史。
- 预期：Codex 收到的思考记录编号不是 `msg_f836e1c0-…` 原样，而是带标记的另一个字符串；从这个字符串里看不出 5 这个渠道编号。下次请求带回这个编号时，中台能读出它来自 5 号渠道，并还原出原编号。

**用例（流式）**
- 场景：同上，但 Codex 用流式请求。
- 操作：上游先发 `response.output_item.added`，再发若干条思考摘要增量，最后发 `response.output_item.done` 和 `response.completed`。
- 预期：这些事件里出现的这条思考记录的编号全部是同一个带标记的字符串，和非流式请求下的写法规则一致。

**用例（Claude 格式）**
- 场景：员工用 Claude Code 通过中台请求 Claude 模型，请求落在 7 号渠道，上游返回一个带签名的 thinking 块。
- 操作：Claude Code 收到回答。
- 预期：thinking 块的签名是带标记的字符串，看不出 7 这个渠道编号；思考正文不变。

**用例（异常：标记被改动）**
- 场景：有人把 Codex 历史里某条带标记的编号改掉一个字符，再发给中台。
- 操作：中台读这条思考记录的标记。
- 预期：中台读不出渠道，这条思考记录按"没有标记"处理，请求本身不报错。

## 约束
- C1：Responses 格式的响应里，每条 `type` 为 `reasoning` 的输出条目，返回给客户端的 `id` 都带渠道标记。标记里的渠道是这次实际回答的渠道（重试换过渠道时，是最后成功的那个）。
- C2：流式响应里，同一条思考记录在所有事件中的编号都是同一个带标记的字符串。这些事件包括条目新增、条目完成、思考摘要和思考正文的各类增量、最终的完整响应，以及其他带这条记录 `item_id` 的事件。
- C3：中台自己把聊天格式、Claude 格式、Gemini 格式的上游回复转成 Responses 格式时，生成的思考记录同样带标记。
- C4：开了透传的渠道、走 WebSocket 的 Responses 请求，返回的思考记录同样带标记。
- C5：Claude 格式的响应里，`thinking` 块的 `signature` 和 `redacted_thinking` 块的 `data` 返回给客户端时带渠道标记；流式时签名增量里的值同样带标记。思考正文不变。
- C6：标记用中台的密钥加密：标记字符串里不出现明文的渠道编号；同一渠道的两条思考记录，标记部分不完全相同；标记被改动任一字符后，中台读不出渠道。
- C7：带标记的编号能还原出上游返回的原值，一个字节都不差。
- C8：思考记录以外的条目（消息、工具调用等）的编号和内容不改。
- C9：标记用的密钥是中台已有的固定密钥（部署时配置的 `CRYPTO_SECRET`，没配时用 `SESSION_SECRET`）。中台重启后、或请求换到另一个节点处理时，只要这把密钥没变，之前发出的标记照样读得出；密钥变了（包括两项都没配、每次启动随机生成），之前的标记全部读不出。

## 验收
- [ ] C1：非流式 Responses 请求落在 5 号渠道，上游返回编号 `msg_x` 的思考记录 → 客户端收到的编号不等于 `msg_x`，中台读它得到渠道 5 和原编号 `msg_x`；第一次落在 3 号渠道失败、重试落在 5 号渠道成功 → 读出的渠道是 5。
- [ ] C2：流式请求，上游在 added、摘要增量、done、completed 四类事件里都带了编号 `rs_y` → 客户端收到的这四类事件里编号都是同一个带标记字符串，读出原编号 `rs_y`。
- [ ] C3：Responses 请求转聊天格式发往上游，上游返回 reasoning_content → 客户端收到的思考记录编号带标记，读出这次的渠道。
- [ ] C4：开透传的渠道、WebSocket 请求各发一次 → 返回的思考记录编号都带标记，读出这次的渠道。
- [ ] C5：Claude 格式请求落在 7 号渠道，上游返回签名 `sig_z` 的 thinking 块和一个 redacted_thinking 块 → 客户端收到的签名和 data 都带标记，分别读出原值和渠道 7；思考正文和上游一致；流式时签名增量同样带标记。
- [ ] C6：用另一把密钥读同一个标记 → 读不出渠道；同一渠道两条思考记录的标记部分不同；改动标记任一字符 → 读不出渠道。
- [ ] C7：上游编号、签名含特殊字符（`+`、`/`、`=`、`-`、`_`）→ 还原出的值和原值逐字节相同。
- [ ] C8：同一响应里的消息条目、工具调用条目的编号和内容和上游一致。
- [ ] C9：用同一把密钥重新初始化（模拟重启或另一个节点）后读之前生成的标记 → 读出原渠道和原值；换一把密钥后读 → 读不出。

## 验证路径
1. 用 Codex 分别以非流式、流式请求一个 deepseek 渠道和一个 GPT 渠道 → 抓到的响应里思考记录编号都不是上游原值，带标记。
2. 用 Claude Code 请求一个 Claude 渠道 → 抓到的响应里 thinking 块签名带标记，正文不变。
3. 把第 1 步拿到的编号改一个字符后发回 → 中台按没有标记处理，请求正常返回。
