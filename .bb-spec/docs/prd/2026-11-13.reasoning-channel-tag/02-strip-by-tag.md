# 按标记清理思考记录

## 用户故事
### P0：作为员工，我希望在同一段对话里切换模型后请求不报错，以便对话能一直进行下去

**用例（主路径：手动切模型）**
- 场景：员工小李在 Codex 的一段对话里，先手动选 deepseek 聊了两轮（5 号渠道），两小时后手动改成 GPT 模型继续（8 号渠道）。历史里有 3 条 deepseek 的思考记录：都没有摘要，正文是明文。
- 操作：小李发出新问题。
- 预期：8 号渠道收到的请求里没有这 3 条思考记录，GPT 正常回答，不报 400；服务器日志记下这次请求清理了 3 段思考记录。

**用例（主路径：同一渠道连续对话）**
- 场景：小李一直用 deepseek（5 号渠道）做一个带工具调用的任务，历史里有 4 条 5 号渠道生成的思考记录。
- 操作：Codex 把工具结果发回中台继续。
- 预期：5 号渠道收到的 4 条思考记录和上游当初返回的完全一样（编号、内容都还原），deepseek 正常继续。

**用例（auto 换渠道）**
- 场景：小王用 auto，前一轮落在 8 号渠道，留下 2 条带摘要和加密内容的思考记录、1 条只有加密内容的思考记录；这一轮升档落在 9 号渠道。
- 操作：小王发出新问题。
- 预期：9 号渠道收到 2 条只有摘要的思考记录（没有编号、没有加密内容），只有加密内容的那条整条去掉；使用日志详情「智能路由」一块显示"上一轮用的渠道不同，已清理 3 段"。

**用例（Claude 格式）**
- 场景：员工用 Claude Code 通过 auto，历史里有 7 号渠道生成的 thinking 块，这一轮落在 6 号渠道。
- 操作：发出新请求。
- 预期：6 号渠道收到的请求里没有这些 thinking 块，不报签名错误。

**用例（异常：老对话）**
- 场景：改版前就存在的对话，历史里的思考记录都没有标记。
- 操作：员工继续这段对话，请求落在任一渠道。
- 预期：这些思考记录都按"渠道不同"清理，请求不报错。

## 约束
- C1：每次发往上游之前（包括重试换渠道之后），中台逐条检查请求历史里的思考记录。Responses 格式检查 `input` 里 `type` 为 `reasoning` 的条目，Claude 格式检查 assistant 消息里的 `thinking`、`redacted_thinking` 块。
- C2：标记读得出来、而且标记里的渠道就是这次要发的渠道 → 把编号（Claude 格式是签名或 data）还原成上游当初返回的原值，其余内容原样发送。
- C3：标记里的渠道不是这次的渠道、没有标记、或标记读不出来 → 清理：
  - Responses 格式：去掉编号和加密内容，保留摘要；没有摘要的整条去掉。这次的渠道要把请求转成聊天格式时，整条去掉，摘要也不留。
  - Claude 格式：去掉 thinking 和 redacted_thinking 块；去掉后变空的 assistant 消息整条删除；请求以工具结果结尾、而这一轮第一条 assistant 消息的思考块被清掉时，这次请求的思考设置从开启改为关闭。
- C4：是否清理只看每条思考记录自己的标记，不看智能路由会话里记的上一次渠道，也不看请求走没走 auto。
- C5：开了透传的渠道、走 WebSocket 的 Responses 请求，按 C1～C3 同样处理。请求里没有思考记录时，透传的请求体原样发送，一个字节都不改。
- C6：清理了思考记录时，服务器日志记一行，写明这次请求清理了几段。走 auto 的请求，使用日志详情「智能路由」一块照旧显示"上一轮用的渠道不同，已清理 X 段"；不走 auto 的请求，使用日志界面不新增内容。
- C7：思考记录以外的历史条目（消息、工具调用、工具结果等）不因这项处理而增减或改变内容。
- C8：Responses 请求里用 `{"type":"item_reference","id":...}` 按编号引用条目时：编号是标记、标记里的渠道就是这次的渠道 → 编号还原成原值；是标记但渠道不同、或标记读不出 → 整条去掉，计入清理段数；不是标记（没有 `rtag_` 前缀）→ 原样保留。这次的渠道要把请求转成聊天格式时，引用条目一律整条去掉：聊天格式的上游没法按编号取已存的条目。

## 验收
- [ ] C1/C2：请求历史里有 4 条标记为 5 号渠道的思考记录，发往 5 号渠道 → 上游收到的 4 条和当初上游返回的逐字段相同（编号是原值）；第一次发往 3 号渠道失败、重试发往 5 号渠道 → 第一次全部清理，重试那次全部还原。
- [ ] C3（Responses）：历史里 2 条带摘要和加密内容、1 条只有加密内容、3 条没有摘要只有明文正文的思考记录，都标记为 8 号渠道，发往 9 号渠道 → 上游收到 2 条只有摘要、没有编号和加密内容的思考记录，其余 4 条不在；同样的历史发往一个要转成聊天格式的渠道 → 6 条全部不在。
- [ ] C3（Claude）：一条 assistant 消息里有标记为 7 号渠道的 thinking 块和一个文本块，另一条 assistant 消息只有 redacted_thinking 块，发往 6 号渠道 → 上游收到的第一条只剩文本块，第二条整条不在；请求以工具结果结尾、这一轮第一条 assistant 消息的思考块被清掉、客户端开了思考 → 上游收到的思考设置是关闭。
- [ ] C3（无标记、标记损坏）：没有标记的思考记录、标记被改动一个字符的思考记录，发往任一渠道 → 都被清理，请求正常发出。
- [ ] C4：智能路由会话里记的上一次渠道是 9，历史里的思考记录标记为 8，这次发往 9 → 被清理；会话记录是 8，标记为 9，这次发往 9 → 还原保留；没有会话记录（不走 auto）的请求同样按标记处理。
- [ ] C5：开透传的渠道、WebSocket 请求，按 C1/C3 的用例各跑一次 → 结果和非透传 HTTP 请求一致；请求里没有思考记录时，透传渠道收到的请求体和客户端发来的逐字节相同。
- [ ] C6：清理了 3 段 → 服务器日志有一行写明清理了 3 段；走 auto 的请求使用日志详情显示"上一轮用的渠道不同，已清理 3 段"；不走 auto 的请求使用日志详情没有新增内容。
- [ ] C7：用例里的消息、工具调用、工具结果条目在上游请求里数量和内容不变。
- [ ] C8：`item_reference` 引用标记为 5 号渠道的思考记录（原编号 `rs_r`），发往 5 号渠道 → 上游收到编号 `rs_r`；同样的引用发往 6 号渠道 → 这一条不在上游请求里，清理段数加 1；引用编号 `msg_1`（不是标记）→ 原样发送；同样的引用发往一个要转成聊天格式的渠道 → 上游请求里没有对应这条引用的任何消息。

## 验证路径
1. Codex 里先手动用 deepseek 聊两轮，再手动切 GPT 发一条 → 不报 400，服务器日志有清理记录。
2. 同一段对话切回 deepseek 继续带工具调用的任务 → deepseek 正常回答。
3. auto 让请求先后落到两个渠道 → 第二个渠道收到的请求里没有第一个渠道的原始思考编号和加密内容，使用日志详情显示已清理段数。
4. Claude Code 通过 auto 在两个 Claude 渠道之间切换 → 不报签名错误。
