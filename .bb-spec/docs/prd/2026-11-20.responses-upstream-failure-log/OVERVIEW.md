# 记录 Responses 流式请求的上游失败原文

## 背景与问题
管理员和 AI 排查问题时，看不出上游为什么返回失败。2026-11-13 到 11-19 这 7 天，生产服务器上有 842 次 `/v1/responses` 流式请求被上游判为失败（上游发了 `response.failed` 事件），主要出在渠道 #7 和 #4。这些请求不扣费，这是有意的设计；问题是失败原因一点都没留下来：

- 消费日志的流状态里只有"失败"两个字，没有错误码、错误类型，也没有错误消息。
- 服务器日志里也没有记录上游给的错误内容。

非流请求失败时，服务器日志会记一行 `channel error (...)`，里面带着截断、脱敏后的上游错误原文。流式请求没有对应的记录，所以管理员只能去上游控制台碰运气，或者在后台点测试，试试能不能复现。

## 目标
- 上游在流式 Responses 请求里每发一个失败事件，服务器日志就多一行，记下渠道号、事件类型、错误码、错误类型和错误消息。管理员或 AI 按请求编号，就能查到这个请求的上游失败原因。

## 非目标
- 非流请求：失败时已经会记 `channel error` 日志，这次不动。
- 消费日志和管理后台界面：不加字段，也不改显示。
- 计费：失败请求扣不扣费，规则不变。
- 不记用户的请求内容，只记上游返回的错误信息。

单一子需求，无依赖。

## 整体验证路径
1. 用一个 mock 上游（模拟上游的测试服务）在流式 Responses 请求里发 `response.failed`，`response.error` 里带 code、type、message，分别走 HTTP 直接转发、Responses 转 Chat、WebSocket 三种方式 → 每种方式的服务器日志里各有一行 ERR，带请求编号、渠道号、事件类型和这三项原文。
2. 让 mock 上游发一个 `error` 为 null 的 `response.failed` → 服务器日志里有一行 ERR，注明上游没给错误信息。
3. 对比第 1 步前后：客户端收到的内容、消费日志、扣费都和改动前一样。

## 决策记录
- **只写服务器日志，不写消费日志的管理员区**。原因：这次要解决的是"AI 和管理员排查时查得到"。服务器日志就是 MCP 日志查询读的那一份，写进去就能查到，管理后台界面也不用改。被否决的方向有两个："服务器日志加消费日志管理员区"，要改界面、出原型，工作量多出约一半；"只写消费日志管理员区"，AI 用 MCP 查不到。
- **三种流式方式全覆盖**：HTTP 直接转发、Responses 转 Chat、WebSocket 现在都只标记失败、不留原文，属于同一个问题，只修一种的话另外两种照样查不到。被否决的方向是只修 HTTP 直接转发。
- **上游没给错误信息时照样记一行**。原因："上游没给原因"本身就是排查结论，不记的话就分不清是上游没给，还是代码漏记了。
- **每个失败事件各记一行**，不是每个请求只记一行。原因：前后几个事件带的信息可能不一样，一个请求里的失败事件很少超过两个，不会刷屏。
- **截断、脱敏、日志级别都跟非流的 `channel error` 日志一致**：原文最多保留 2048 字节（开了 DEBUG 时不截），脱敏用同一个函数，把 `api_key:xxx` 写法的密钥、上游地址、网址里的查询参数和 IP 换掉，级别用 ERR。原因：两类日志排查时会放在一起看，规则一致才不会误判。现有脱敏函数不处理裸露的 `sk-` 开头的密钥；这个问题在 `channel error` 日志里本来就有，要改得动公共脱敏函数、影响所有调用方，所以这次不处理，另外评估（exec 阶段用户确认）。
- **质疑结论**：起因是先发现"842 次请求没扣费"，查代码确认这是上游明确失败、有意不扣费，不是 bug。真正缺的是失败原因，所以这次需求只补记录，不改计费。
