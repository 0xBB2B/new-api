# 所有条目编号按生成它的渠道决定去留

## 背景与问题
中台已经给思考记录的编号打了加密的渠道标记：同一渠道生成的原样发回，别的渠道生成的清理掉。上线后测试中台又报 400：`Invalid 'input[17].id': 'msg_bc5a6688-…'. Expected an ID that begins with 'ctc'.`

报错的是 deepseek 同一轮生成的一条工具调用（`custom_tool_call`），编号是 `msg_<uuid>`。OpenAI 对每类条目的编号前缀有要求：思考记录 `rs_`、自定义工具调用 `ctc_`、函数调用 `fc_`、消息 `msg_`。本机 Codex 记录里，deepseek 和 glm 上游生成的工具调用编号都是 `msg_<uuid>`，共 98 条；切到 GPT 渠道后，这些编号会被原样转发，然后被拒收。思考记录以外的条目，中台现在一律原样转发。GPT 生成的消息还带加密内容（`encrypted_content`），换到另一个 OpenAI 账号时，它和思考记录的加密内容一样可能失效。

## 目标
- 同一段对话里，别的渠道生成的任何条目的编号和加密内容都不会被原样转给上游，切模型后不因此报错。
- 同一渠道连续对话时，所有条目的编号原样发回。
- 改版前就存在的老对话继续使用时也不报错。

## 非目标
- 工具调用与结果之间的配对编号 `call_id`：不改。
- Claude 格式请求里 `tool_use` 的编号及 `tool_result` 的对应编号：不改。
- 响应本身的编号（`resp_` 开头的 `id`）、`previous_response_id`：不改。
- 使用日志与服务器日志里的"清理段数"：仍只统计思考记录，去掉其他条目的编号不计入。
- 思考记录现有的打标记与清理规则：不变。
- 其他字段的跨厂商差异：工具调用的 `namespace`、`status`，消息的 `phase`、`annotations`、`logprobs`，以及 `agent_message`、`compaction` 这类条目类型。这些是否会被上游拒收，另行用真实上游实测后再定。

## 整体验证路径
1. 在 Codex 里先手动用 deepseek 做一个需要调用工具的任务，再手动切到 GPT 发一条 → 不报 400；GPT 收到的历史里，deepseek 生成的工具调用、消息都没有编号，`call_id` 和内容都在。
2. 同一段对话一直用 GPT 做带工具调用的任务 → GPT 收到的历史里，它自己之前生成的工具调用、消息编号都是它当初返回的原值。
3. 继续今天报错的那段老对话并切到 GPT → 不报 400。

## 决策记录
- **2026-11-13，用户定：所有带编号的条目都打渠道标记，规则和思考记录相同。** 否掉了"其他条目一律去掉编号"：同一渠道连续对话时也会丢编号。OpenAI 文档写明函数调用、自定义工具调用的 `id` 是可选字段，配对靠 `call_id`，所以去掉编号不影响对话内容。
- **2026-11-13，用户定：标记是别的渠道、或标记读不出的条目，去掉编号、保留条目。** 否掉了"整条去掉"：会把工具调用和它的结果拆散。
- **2026-11-13，用户定：没有标记的非思考条目一律去掉编号。** 这类条目包括客户端自己生成的用户消息、工具结果，以及改版前老对话里上游生成的工具调用。否掉了"原样保留"：老对话切到 GPT 仍会 400。代价是客户端自己生成的编号也会被拿掉；按文档不影响上游，但没有实测。
- **2026-11-13，用户定：纳入所有带编号的条目，不只列工具调用。** 以后出现新的条目类型也自动覆盖，不用再碰到一次修一次。
- **2026-11-13，用户定：消息等非思考条目的加密内容一并按标记处理。** 同渠道保留，其他情况去掉。依据：思考记录的加密内容绑定账号已有证据；消息上的加密内容是否同样绑定，没有查到，按同理处理。其他字段差异先实测，不并入本需求。
- **Claude 格式不纳入。** `tool_use` 编号必须和 `tool_result` 的 `tool_use_id` 成对改写，改动面大。目前没有 Claude 因编号格式拒收的证据；Claude 只检查编号字符集、不检查前缀，这一点没有验证。
- 本需求扩展已合并需求 `2026-11-13.reasoning-channel-tag` 的范围。那份需求里"思考记录以外的条目编号和内容不改"的规定由本需求取代：条目内容仍不改，编号按本需求处理。
