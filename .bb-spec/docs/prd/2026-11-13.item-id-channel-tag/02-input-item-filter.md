# 按标记处理非思考条目的编号

## 用户故事
### P0：作为员工，我希望先用 deepseek 调用过工具的对话切到 GPT 后不报错，以便对话能继续

**用例（主路径：切渠道）**
- 场景：小李的对话历史里有 deepseek（5 号渠道）生成的自定义工具调用（编号是 5 号渠道的标记，`call_id` `call_1`）、Codex 自己生成的工具结果（编号 `ctco_<uuid>`，`call_id` `call_1`）和用户消息（编号 `msg_<uuid>`）。这一轮落在 GPT 的 8 号渠道。
- 操作：小李发出新问题。
- 预期：8 号渠道收到的这三条条目都没有 `id` 字段；工具调用和结果的 `call_id` 都是 `call_1`，内容不变；不报 400。

**用例（主路径：同渠道连续对话）**
- 场景：小李一直用 GPT（8 号渠道），历史里有 8 号渠道生成的工具调用（标记，原值 `ctc_x`）和消息（标记，原值 `msg_y`）。
- 操作：Codex 把工具结果发回中台继续。
- 预期：8 号渠道收到的工具调用编号是 `ctc_x`，消息编号是 `msg_y`。

**用例（老对话）**
- 场景：改版前的对话，历史里有 deepseek 生成的、没有标记的工具调用（编号 `msg_bc5a6688-…`）。
- 操作：员工继续这段对话并切到 GPT。
- 预期：GPT 收到的这条工具调用没有 `id` 字段，不报 400。

## 约束
- C1：每次发往上游之前（包括重试换渠道之后），中台检查 Responses 请求 `input` 里思考记录、`item_reference` 以外的每条条目。
- C2：`id` 是标记、读得出、渠道就是这次的渠道 → 还原成原值，其余原样。
- C3：`id` 是别的渠道的标记、标记读不出、不是标记、或条目没有 `id` → 去掉 `id` 字段和条目顶层的 `encrypted_content` 字段，条目其余内容（含 `call_id`）原样保留，条目不删除。C2 的情况下 `encrypted_content` 原样保留。
- C4：这项处理不计入清理段数，不改变使用日志和服务器日志里的清理记录。
- C5：开了透传的渠道、走 WebSocket 的请求同样处理。请求里没有任何带 `id` 或顶层 `encrypted_content` 的非思考条目时，透传的请求体原样发送，一个字节都不改。
- C6：思考记录和 `item_reference` 的处理规则不变。

## 验收
- [ ] C1/C3：用例"切渠道"的三条条目发往 8 号渠道 → 上游收到的三条都没有 `id`，`call_id` 都是 `call_1`，类型和其他字段与客户端发来的一致，条目数量不变。
- [ ] C2：用例"同渠道"发往 8 号渠道 → 工具调用 `id` 为 `ctc_x`、消息 `id` 为 `msg_y`；第一次发往 3 号渠道失败、重试发往 8 号渠道 → 第一次去掉编号，重试那次还原。
- [ ] C3（加密内容）：GPT 8 号渠道生成的消息（编号是 8 号渠道的标记，带 `encrypted_content` `E`）→ 发往 8 号渠道时 `encrypted_content` 为 `E`；发往 9 号渠道时没有 `id` 和 `encrypted_content`，`role`、`content` 不变。
- [ ] C3（篡改）：编号是被改过一个字符的标记 → 去掉 `id`，请求正常发出。
- [ ] C4：只有非思考条目被去掉编号 → 智能路由结果的清理段数为 0，使用日志不显示"已清理"。
- [ ] C5：透传渠道、WebSocket 请求按上面三种情况各跑一次 → 结果与非透传 HTTP 一致；请求里的非思考条目都不带 `id` 和 `encrypted_content` 时，透传渠道收到的请求体与客户端发来的逐字节相同。
- [ ] C6：思考记录、`item_reference` 的现有用例结果不变。

## 验证路径
1. Codex 里先用 deepseek 调用工具，再切 GPT → 不报 400，抓到的上游请求里 deepseek 那几条没有 `id`。
2. 一直用 GPT 调用工具 → 上游请求里 GPT 自己的条目编号是原值。
3. 继续今天报错的老对话并切 GPT → 不报 400。
