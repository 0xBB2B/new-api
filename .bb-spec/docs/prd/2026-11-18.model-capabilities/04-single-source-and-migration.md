# 思考能力只留一处并搬迁旧数据

## 用户故事
### P0：作为管理员，我想升级后不用重新配置思考等级，且以后只在模型管理页配置，以便智能路由和调用方看到同一份能力

**用例（主路径）**
- 场景：升级前，内置表里 `gpt-6.2-sol` 是 none 到 max 六档；管理员在「模型思考能力」卡片里把 `glm-5.3` 覆盖成 low、high；模型管理里已有一条前缀记录 `gpt-6`（配了描述和接口配置），没有 `gpt-6.2-sol` 的完全匹配记录。
- 操作：升级并启动服务，打开模型管理页和智能路由设置页。
- 预期：
  - 模型管理里多了 `gpt-6.2-sol` 的完全匹配记录，思考等级为 none 到 max 六档，描述和接口配置与 `gpt-6` 相同。
  - `glm-5.3` 记录的思考等级是 low、high（用的是卡片里的覆盖值，不是内置表的 low、high、max）。
  - 智能路由设置页只剩「虚拟模型」卡片。
  - 用以 `gpt-6.2-sol` 为档位模型的虚拟模型发请求，思考力度换档结果与升级前一致。

**用例（边界 / 异常）**
- 场景：服务第二次启动。预期：记录数不变，不改动管理员升级后在模型管理页改过的思考等级。
- 场景：管理员在模型管理页把 `qwen4-max` 的思考等级清空成未配置。操作：以 `qwen4-max` 为档位模型的虚拟模型收到请求。预期：按「能力未确认」处理，在 low、medium、high 里换档。
- 场景：编辑虚拟模型时选了未配置思考等级的 `foo-model`。预期：「思考力度」那一行右侧显示黄色徽标「能力未确认」，提示气泡写「这个模型还没有配置思考等级，可在「模型管理」里编辑这个模型，在「模型能力」里补充」。

## 约束
- C1：一个模型名的思考能力按以下顺序取值，智能路由（档位思考力度换档、打分模型力度、虚拟模型编辑弹窗里的档位选项和徽标）与 `/v1/models` 用同一顺序：
  1. 命中这个名字的模型记录里配置的思考等级（命中规则：完全匹配优先，其次前缀、后缀、包含，同一种规则里取第一条命中的，整条记录一起生效）；
  2. 命中记录没配思考等级、或没有命中记录时，用代码里的 2026 年 Claude、Gemini 3.x 推算规则（以及 relaykit 判定不支持思考的 Gemini 模型，不论年份，推算为不支持思考）；
  3. 都没有时为「能力未确认」，智能路由按只支持 low、medium、high 处理。
- C2：运行时取思考能力不查按型号名写死的档位表（升级搬迁用的快照只在搬迁时读一次）；新型号的思考等级只能在模型管理页（编辑抽屉或「能力配置 JSON」）配置。
- C3：升级搬迁。从上一个版本升级后第一次启动时，把下面两份数据写进模型记录的思考等级：
  - 升级前「模型思考能力」卡片里的每一条覆盖（含不支持思考）；
  - 升级前内置表里的全部 32 个型号（含 gpt-4o、gpt-4.1、gpt-4.1-mini 三个不支持思考的型号）。
  同一个型号两份数据都有时，用卡片里的覆盖值。
- C4：搬迁写到这个型号名的完全匹配记录上：已有完全匹配记录 → 只写它的思考等级，其他资料不动；没有 → 新建一条完全匹配记录。新建时，如果这个名字被前缀、后缀、包含规则的记录命中，复制命中那条记录的描述、图标、标签、厂商、接口配置、广场可见状态、是否允许同步资料；没有命中时，其他资料与在页面上手动新建记录的默认值相同。
- C4b：型号名正好是一条前缀、后缀、包含规则记录的名字时，跳过这个型号并记日志，不新建同名记录，也不改那条记录。
- C5：搬迁只做一次。之后再启动不新建记录，也不覆盖管理员在模型管理页改过的思考等级；搬迁中途失败时，下次启动从头重做且结果与一次做完相同，不产生重复记录。
- C6：搬迁后，按搬迁时写的原名（与快照、覆盖里的名字完全相同）取思考能力，结果（档位列表、是否不支持思考）与升级前一致。带日期后缀或大小写不同的名字（如 `gpt-5.5-2026-03-05`、`GPT-5.5`）没有自己的模型记录时为能力未确认。
- C7：搬迁完成后，「模型思考能力」卡片原来存的覆盖数据从数据库里删除。
- C8：智能路由设置页（系统设置 → 请求策略 → 智能路由）删掉「模型思考能力」卡片，只剩「虚拟模型」卡片，虚拟模型卡片本身不变；对应的读写这份覆盖数据的接口一并去掉。
- C9：编辑虚拟模型弹窗里，所选模型按 C1 取不到思考等级（能力未确认）时，「思考力度」那一行右侧仍显示黄色徽标「能力未确认」；鼠标移上去或聚焦时，提示气泡文案为「这个模型还没有配置思考等级，可在「模型管理」里编辑这个模型，在「模型能力」里补充」。
- C10：在模型管理页改了思考等级（编辑抽屉或「能力配置 JSON」保存）后，下一个请求的智能路由换档就用新值，不用重启。

## 验收
- [ ] C1：同一个模型名分别有完全匹配记录、只有前缀记录、只有 Claude 推算规则、什么都没有四种情况 → 智能路由换档和 `/v1/models` 都按约束顺序取值，两边结果一致。
- [ ] C2：在模型管理页新建 `gpt-7-sol` 并配置 low、high → 不改代码，智能路由立即按 low、high 换档。
- [ ] C3：用带卡片覆盖（含一条不支持思考）的上一版本数据库升级 → 32 个内置型号和所有覆盖型号都有完全匹配记录且思考等级正确；同时出现在两份里的型号用的是覆盖值。
- [ ] C4：已有完全匹配记录 `gpt-5.5`（有描述）→ 搬迁后描述不变、思考等级写入；被前缀记录 `gpt-6` 命中的 `gpt-6.2-sol` → 新记录其他资料与 `gpt-6` 相同；无命中的 `glm-5.2` → 新记录其他资料为默认值。
- [ ] C4b：已有名为 `gpt-5.4` 的前缀记录时搬迁 → 不新建同名完全匹配记录，前缀记录不变，日志有一条跳过记录。
- [ ] C5：连续启动两次 → 记录数不变；升级后把 `gpt-6.2-sol` 改成 low、high 再重启 → 仍是 low、high；搬迁中途中断后重启 → 记录不重复，结果与一次做完相同。在 SQLite、MySQL、PostgreSQL 上分别验证。
- [ ] C6：升级前后，对每个搬迁型号按原名比较智能路由取到的思考能力 → 一致；无记录的 `gpt-5.5-2026-03-05` 为能力未确认。
- [ ] C7：搬迁后数据库里没有卡片的覆盖数据。
- [ ] C8：智能路由设置页只显示「虚拟模型」卡片；调用原来读写覆盖数据的接口 → 不存在。
- [ ] C9：编辑弹窗选未配置思考等级的模型 → 徽标和提示气泡文案与约束一致；选已配置的模型 → 不显示徽标。
- [ ] C10：在编辑抽屉改 `qwen4-max` 的思考等级并保存 → 不重启，下一个经智能路由到 `qwen4-max` 的请求按新档位换档。

## 验证路径
1. 用上一个版本建库，在「模型思考能力」卡片里覆盖两个型号（其中一个不支持思考），建一条前缀记录 `gpt-6`。
2. 升级启动 → 检查模型管理里的记录、思考等级、复制来的资料；智能路由设置页只剩「虚拟模型」卡片。
3. 重启一次 → 记录数和思考等级不变。
4. 在模型管理页改一个档位模型的思考等级 → 不重启，发请求，日志里的换档结果用新值。
5. 编辑虚拟模型，选一个未配置的模型 → 显示「能力未确认」和新的提示文案。
