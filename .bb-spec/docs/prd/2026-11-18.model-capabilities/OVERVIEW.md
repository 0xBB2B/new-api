# 模型能力配置与 /v1/models 返回

## 背景与问题
接 API 的客户端（调用 `/v1/models` 拿模型列表的程序）不知道每个模型能选哪几档思考等级、能不能收图片、能不能出图片、上下文有多大、最多输出多少 token。用户在客户端里选了模型不支持的思考等级，请求会被上游拒绝，或者被网关悄悄换成别的档位；传了图片给不收图片的模型，也只能等上游报错。

网关里，模型支持哪几档思考等级目前存在两处：一处是写在代码里的内置表，按型号名列出约 30 个型号的档位；另一处是智能路由设置页里的「模型思考能力」卡片，管理员可以在这里按模型名覆盖。每出一个新型号都要改代码、发版，内置表才能认得它。输入输出模态、上下文大小、最大输出 token 这几项，网关里目前哪里都没有存。

## 目标
- 管理员在模型管理页给模型配置思考等级、输入模态、输出模态、上下文大小、最大输出 token，保存后立即生效，不用改代码或发版。
- 管理员能把全部模型的能力配置看成一段 JSON，可以复制、下载，改完或粘贴新内容后整体替换保存。
- `/v1/models`（OpenAI 格式）对配置过的模型返回这些能力，字段命名照 OpenRouter。
- 模型思考能力只在模型管理页这一处配置。智能路由和 `/v1/models` 用同一份数据，代码里没有按型号名写死的档位表。

## 非目标
- `/v1/models` 的 Anthropic 格式、Gemini 格式不加能力字段，保持各自官方的字段。
- 定价页 `/api/pricing`、用户模型列表 `/api/user/models` 不加能力字段。
- 网关不按配置的能力去拦截请求：例如给不收图片的模型传了图片，照常转发。
- 「同步官方资料」不同步这几项能力。
- 智能路由虚拟模型（如 `auto`）不返回能力字段，也不配置能力。
- 2026 年的 Claude、Gemini 3.x 按型号名推算思考档位的规则保留在代码里，不搬进模型记录。

## 整体验证路径
1. 从上一个版本升级启动 → 模型管理页里能看到内置表原有的 32 个型号和「模型思考能力」卡片里覆盖过的模型，它们的思考等级跟升级前一致；智能路由设置页已经没有「模型思考能力」卡片。
2. 在模型管理页编辑 `gpt-6.2-sol`，配置输入模态 `text`、`image`，上下文大小 1050000，保存 → 用 API 令牌请求 `GET /v1/models`，`gpt-6.2-sol` 的对象里返回 `context_length: 1050000`、`architecture.input_modalities: ["text","image"]`，以及升级时搬过来的 `reasoning.supported_efforts`。
3. 打开「能力配置 JSON」，把 `gpt-6.2-sol` 的 `context_length` 改成 900000，删掉 `qwen4-max` 整段，预览 → 预览显示 `gpt-6.2-sol` 更新、`qwen4-max` 清空；替换保存 → `/v1/models` 里 `gpt-6.2-sol` 返回 900000，`qwen4-max` 没有能力字段。
4. 用一个通过智能路由选到 `qwen4-max` 的虚拟模型发请求 → 日志显示它的思考能力为「能力未确认」，按 low、medium、high 换档。

## 决策记录
- **问题定性**（用户 2026-11-18 认可）：客户端不知道每个模型能选哪几档思考等级，选错了会被上游拒绝或被网关改掉。用户随后把范围扩大到图片输入输出、上下文大小、最大输出 token，并要求不改代码就能更新。
- **返回接口选 `/v1/models`**（用户选）：否掉 `/api/pricing`、`/api/user/models`。只加在 OpenAI 格式里（用户选），跟现有扩展字段 `supported_endpoint_types` 一样；否掉三种格式都加，因为 Anthropic、Gemini 格式是照各自官方定义的。
- **字段命名照 OpenRouter**（用户选）：`context_length`、`top_provider.max_completion_tokens`、`architecture.input_modalities` / `output_modalities`、`reasoning.supported_efforts`。查过的其他做法：models.dev 用 `limit.context`、`modalities.input`、`reasoning_options`；OpenAI Codex 客户端读的 ChatGPT 后台接口用 `supported_reasoning_efforts`；OpenAI 公开 `/v1/models` 没有这类字段。选 OpenRouter 是因为它跟本项目同类，都是聚合网关，适配它的客户端最多。
- **未配置的项不返回**（用户选）：「能力未确认」的模型不返回猜出来的 low/medium/high，否掉"返回档位并标来源"和"只返回档位不标来源"；虚拟模型不返回（用户选），因为它的思考等级由网关按打分自己选。确认不支持思考的模型返回 `supported_efforts: []`（用户选），让客户端能分清"不支持"和"不知道"，否掉 OpenRouter 那样直接省掉字段。
- **配置放在模型管理页**（用户选）：否掉服务器上的配置文件（要登录服务器改、要重新加载、多台机器各改各的）和单独一个 JSON 设置项（跟模型管理页成了两处）。根源性自检：用户要的是"能力改了不等发版"，存数据库、在后台改一样能做到，而且模型管理页本来就存着每个模型的描述、图标、接口类型。
- **思考能力只留一处**（用户选）：「模型思考能力」卡片删掉，覆盖数据搬进模型记录；否掉保留卡片（两处配置要规定谁优先）。内置表是这个 fork 自己加的（`b0385cf09`，2026-11-06），上游没有，用户选"搬进模型记录后删掉"，否掉"留着当兜底"（新型号仍要改代码，只缓解症状）和"整张删掉不搬"（已有配置会丢）。32 个型号全部搬（用户选），否掉只搬渠道里配了的型号。Claude、Gemini 3.x 的推算规则不按型号名写死，新型号出来不用改代码，所以留在代码里。
- **JSON 配置两种都要**（用户选）：编辑单个模型时能切 JSON 模式；另有一个窗口处理全部模型。导入和导出合成一个「能力配置 JSON」窗口（用户 2026-11-18 原话："导入导出统一到一个按钮popup，直接查看复制或者替换保存"）。
- **整体替换**（用户选方案 B）：保存后每个模型的能力就是 JSON 里写的样子，没写的字段、写 null 的字段都清空，JSON 里删掉的模型能力清空、记录保留。否掉方案 A"合并保存"（没写的保留原值），虽然 A 粘贴一小段时更安全，用户要的是"看到什么就存成什么"；粘贴一小段会清空其他模型的风险，由预览里的清空提示框拦（用户选留）。
- **校验失败整批不保存，保存失败全部不生效**（用户确认）。
- **并发保护用"预览取最新 + 保存查版本"**（用户 2026-11-18 定）：预览时按服务器最新数据对比；保存时发现预览后数据又变了就拒绝，请用户重新预览。项目里「同步官方资料」已有同样做法（`model/model_metadata_sync.go:43`）。否掉只在预览时取最新（预览到保存之间的改动会被悄悄清空），也否掉打开窗口后数据一变就拒绝（多人同时改时容易被打断）。
- **没有记录的模型自动新建完全匹配记录**（用户选）：否掉跳过并列出。这个名字已被前缀、后缀、包含规则的记录命中时，新记录复制那条记录的描述、图标、标签、厂商、接口配置、广场可见状态（用户选），否掉其他资料留空（会让这个模型的描述、接口类型变空）。
- **非完全匹配的记录不进 JSON 窗口**（用户确认建议）：它们的名字不是具体模型名，导出后再导入会变成同名的完全匹配记录；只能在编辑抽屉里改。
- **上下文大小、最大输出 token 不设业务上限**（用户选"任意正整数"），否掉 1 到 1 亿。为了浏览器里的 JavaScript 能精确表示，技术上限取 9007199254740991（2^53−1）。
- **带日期后缀、大小写不同的名字不做兜底匹配**（用户 2026-11-18 定）：升级前内置表查找会先转小写、去掉 `-YYYY-MM-DD` 日期后缀，所以 `gpt-5.5-2026-03-05` 能取到 gpt-5.5 的档位；现在只按模型记录的名称规则匹配，这类名字没有自己的记录时为能力未确认，需要时由管理员建记录。否掉"原名没命中时去日期、转小写再查一次"。
- **界面**：原型 2026-11-18 第 5 版经用户确认。
