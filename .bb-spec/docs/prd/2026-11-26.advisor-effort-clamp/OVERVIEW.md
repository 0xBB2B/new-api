# 顾问这一轮的思考力度按模型能力换档

## 背景与问题
2026-11-25，用户在 Claude Code 里用智能路由的虚拟模型时，被交给顾问（advisor）gpt-6.2-astra 回答，这一轮直接失败。上游 OpenAI API 渠道返回 400：`Unsupported value: 'none' is not supported with the 'gpt-6.2-astra' model. Supported values are: 'low', 'medium', 'high', 'xhigh', and 'max'`。

原因有两层：
- Claude Code 关掉思考时发 `thinking.type=disabled`，智能路由把它记成思考力度 none。顾问这一轮把客户端的力度原样发给上游，不像三个普通档位那样先换成模型支持的档位。
- gpt-6.2-astra 的模型记录里登记了支持 none。这是当初按 ChatGPT 订阅渠道实测加的；OpenAI API 渠道不接受 none。所以即使顾问换档，按这条记录也会认为 none 可以直接发。

现在只能靠用户换个说法、让会话离开顾问，或者打开思考再发，没有办法让这一轮成功。

## 目标
- 顾问这一轮发给上游的思考力度，一定是顾问模型支持的档位；模型不支持思考时不发思考参数。
- gpt-6.2-astra 走 OpenAI API 渠道时，客户端关掉思考的请求交给顾问能成功返回。

## 非目标
- 不给顾问加"思考力度方式"配置，顾问仍然以客户端带的力度为准，只在模型不支持时换档。
- 不按渠道区分模型能力。同一个模型挂在订阅渠道和 API 渠道上，支持的档位只登记一份。
- 不改三个普通档位、打分模型的力度规则。
- 不改日志详情的显示规则；顾问换档后的显示沿用普通档位已有的写法。
- 模型记录的数据不由代码改写。gpt-6.2-astra 去掉 none 由管理员在模型管理页操作，见「整体验证路径」第 1 步。

## 依赖与交付顺序
单一子需求，无依赖。

## 整体验证路径
1. 管理员在模型管理页打开 gpt-6.2-astra 的模型记录，把思考等级里的 none 去掉，保存 → /v1/models 里 gpt-6.2-astra 的思考等级是 low、medium、high、xhigh、max。
2. 用顾问是 gpt-6.2-astra（挂 OpenAI API 渠道）的虚拟模型，在同一会话里连续发不满意的消息直到交给顾问，客户端请求带 `thinking.type=disabled` → 这一轮成功返回，上游收到的力度是 low。
3. 打开这条请求的消费日志详情 → 「智能路由」块的「思考力度」写「low（不覆盖，由 none 升档）」。

## 决策记录
- **顾问也换档，规则和三个普通档位一样**（用户 2026-11-26 选定）：客户端的力度模型支持就照发；不支持就换成支持的档位里最接近的一档，上下一样近取更高的一档；模型不支持思考就去掉思考参数。400 的根源是顾问漏掉了普通档位已有的这一步，补上同一条规则，日志写法也一致。被否决的方向：模型不支持时不发力度参数、让模型自己决定——这样和普通档位的规则不一致，同一个 none 在两处结果不同。
- **改了已合并的规则**：`2026-11-05.smart-routing-effort` 01 的 C9 写着"顾问这一轮照旧用客户端带的值……即使顾问模型不支持也不改写"，`2026-11-04.smart-routing` 04 的 C6 写着"顾问回答时保留客户端传来的思考力度"。当时没有考虑顾问模型不支持客户端力度、上游会拒收的情况。本需求改为：仍以客户端的值为准，只在模型不支持时换档。
- **补上两种读写漏掉的请求**（2026-11-26 审查发现，用户选择修复）：Chat 请求把力度写在 `reasoning` 对象里时，网关读不到，原样发给上游，仍会被拒；Anthropic 请求只带力度、没开思考时，换档后会被替客户端打开思考、去掉 `temperature`。这两处是顾问和「不覆盖」档位共用的读写，一起修。「固定」「跟随打分」档位由管理员定力度，打开思考是有意的，保持原样。被否决的方向：只修顾问——同一个请求在「不覆盖」档位和顾问之间结果不同，没有理由。
- **Chat 请求换档时整个去掉 `reasoning` 对象**（用户 2026-11-26 选定）：曾尝试只删 `reasoning` 里的力度字段、保留 `exclude`，审查实测发现下游解析 `reasoning` 不区分大小写，客户端写 `MAX_TOKENS` 就能留到上游、绕开档位定的力度。整个删除不依赖网关和下游对字段写法的理解一致。代价：客户端设的 `exclude` 在换档时一并去掉，和改动前一样。被否决的方向：不区分大小写地逐个删字段——下游以后多认一种写法，这里又要跟着补。
- **代价**：客户端关掉思考（none）、顾问模型又不支持 none 时，顾问会用 low 思考，比客户端要的多花一些思考 token。普通档位遇到同样情况已经是这样。
- **gpt-6.2-astra 去掉 none，不按渠道区分能力**（用户 2026-11-25 选定）：none 是当初按订阅渠道实测加的，提交说明里已写明挂到 API 渠道会被拒。按渠道区分能力要改模型记录的结构和选渠道的逻辑，代价远大于这次的问题。被否决的方向：模型能力按渠道类型分开登记。代价：gpt-6.2-astra 走订阅渠道时，也不能用 none。
- **质疑结论**：只在模型管理页去掉 none 不够，顾问不换档，none 照样发给上游；只给顾问加换档也不够，模型记录说支持 none，就不会换。两件都要做。
