# 智能路由二期：思考力度自动调整、多接口、配置改版

## 背景与问题
智能路由一期上线后，每个档位只能配一个固定的思考力度（不覆盖 / low / medium / high）。同一档里的问题难度也有高有低，固定力度要么浪费钱，要么想得不够深。不同模型支持的思考力度也不一样：有的到 xhigh、max，有的根本不支持思考，管理员只能凭记忆去配，配错了上游直接报错。

一期的虚拟模型只认一种接口，而且接口是按所选模型自动判断的，判断依据的元数据会出错（例如 DeepSeek 渠道其实能转发 Responses，却被判成只支持 Chat）。用 Claude Code 的员工没法用虚拟模型。

配置弹窗把三档、打分、顾问的全部字段平铺在一页，说明文字多，管理员抓不住重点。

虚拟模型只出现在客户端调用的模型列表接口里，后台的「填入 CC Switch」、密钥模型白名单、演练场都选不到它，员工得手动敲名字。

## 目标
- 档位可以让思考力度跟着打分的「要想多深」自动取值，并限制在管理员配的范围内。
- new-api 只发模型支持的思考力度：配置时只能选到模型支持的档位，请求时超出能力就换成最接近的档位，日志写明实际发了什么、为什么。
- 管理员能看到、也能覆盖每个模型支持哪几档思考力度。
- 一个虚拟模型可以同时接收 Responses、Chat Completions、Anthropic 三种格式的请求，由管理员勾选。
- 配置弹窗一次只显示一组设置，关键字段一屏看完。
- 除渠道模型配置以外，后台选模型的地方都能选到虚拟模型。

## 非目标
- 不支持 Gemini 格式（`/v1beta/models/{model}:generateContent`）的虚拟模型请求。
- 不让 Codex 订阅渠道接收 Anthropic 格式；档位用了这类渠道时，保存会被拦下。
- 打分模型的思考力度不开放配置；顾问不设思考力度，照旧用客户端传来的值。
- 「模型思考能力」表只列档位里用到的模型，不列打分模型和顾问模型，也不做全站通用的模型能力管理页。
- 不做「让 AI 上网查文档自动填能力表」。
- 价格页、模型定价设置、档位模型下拉、渠道模型配置里不出现虚拟模型。
- 打分标签、选档规则、会话规则、降档保护和一期相同，不改。

## 整体验证路径
1. 管理员打开「系统设置 → 请求策略 → 智能路由」，编辑 auto-gpt：接口勾 Responses 和 Anthropic；左栏「档位」→「困难」，思考力度选「跟随打分」，范围 medium～xhigh；保存，再点「保存更改」→ 表格里 auto-gpt 名称下写「Responses / Anthropic 接口」，困难档第二行写「跟随打分 medium～xhigh · …」；「模型思考能力」表里列出三档用到的模型。
2. 员工在 Codex 里用 auto-gpt 发一条会被分到困难档、「要想多深：高」的消息 → 上游收到的思考力度是 high；日志详情「思考力度」一行写「high（跟随打分）」。
3. 同一员工用 Claude Code（Anthropic 格式）请求 auto-gpt → 按同样的规则打分、选档、计费；困难档请求的思考力度同样按跟随打分取值。
4. 管理员在「模型思考能力」里把 gpt-5.6-sol 覆盖成只支持 low / medium / high，保存更改 → 表格里 auto-gpt 困难档那一格标黄并写「超出模型能力，实际按 high 发送」；之后打分「要想多深：高」时仍发 high，打分失败时本该发 xhigh，实际发 high，日志写「high（跟随打分，由 xhigh 降档）」。
5. 普通档模型所在的 subscription 分组只有 Codex 渠道时，在 auto-gpt 勾上 Anthropic 再保存 → 弹窗不关，普通档分组一行写红字「gpt-5.5 在分组 subscription 里只有 Codex 渠道，接收不了 Anthropic 格式」。
6. 员工在密钥页点「填入 CC Switch」、选 Codex → 主模型下拉末尾有 auto-gpt、auto-chat；新建密钥的模型限制里能勾 auto-gpt；演练场只列勾了 Chat 的虚拟模型。

## 决策记录
- **力度跟着「要想多深」取值，再限制在档位配的最低～最高之间**：用户 2026-11-05 提出力度不要固定。「要想多深」本来就是打分标签之一，低→low、中→medium、高→high 的对应最直观；管理员用最低、最高两个值控制成本上限和质量下限。
- **力度可选值扩到 none / minimal / low / medium / high / xhigh / max 七档**：和 relaykit 里已有的思考力度档位一致（`relaykit/relayconvert/reasoning/intent.go`），新模型的 xhigh、max 才能用上。
- **打分失败时跟随打分用最高档**：没有「要想多深」可用时宁可多想，不让答案变差；成本上限仍受「最高」限制。工具结果续跑沿用本轮用户新消息算出的力度；会话里没有记录时，和打分失败一样用最高档，因为同样没有打分结果可以参考。
- **只发模型支持的力度，超出就换成最接近的档位，一样近时取更高的那档**：发不支持的值上游会直接报错。取更高是为了不让回答质量掉下去。「不覆盖」时客户端传来的值也按这条处理。
- **不支持思考的模型去掉思考参数**：例如 gpt-4.1 收到思考参数会报错。配置页对这类模型隐藏力度选项。
- **能力来源：代码内置能力表 + 管理员按模型覆盖**：用户选的。否掉了「每次请求或定时让 AI 上网查文档」：结果不稳定，网页内容可能被注入，慢，还要外网。也否掉了「全部由管理员手配」：工作量大，容易配错。内置表一期覆盖 OpenAI（gpt-5 系列、o 系列）、Claude、Gemini、DeepSeek，取值来自各厂商官方文档。
- **未确认的模型当成只支持 low / medium / high**：这三档是各家支持最普遍的；配置页标「能力未确认」，提醒管理员去补。
- **能力改小后，已存的档位力度不自动改，请求时自动降档，表格里标黄**：能力改小不该让线上请求出错；标黄让管理员看到、自己决定要不要改配置。否掉了「改能力时拦住保存」：会逼管理员先去改每个虚拟模型，顺序很别扭。
- **能力表只列档位用到的模型**：只有档位能设思考力度；打分固定用 low，顾问不设力度，列出来也没有可配的。
- **顾问维持现状，用客户端的力度**：用户选的。顾问是兜底的强模型，一期没有给它配力度，这期不改。
- **接口改成管理员手动勾选，可多选**：一期按模型自动判断接口，依据的元数据会出错（DeepSeek 渠道实际转发 Responses，`relay/channel/deepseek/adaptor.go:87-88`，元数据却只写了 Chat）。用户 2026-11-05 决定由管理员手动选，否掉了「修元数据表」：表靠人维护，迟早又会和渠道实际能力对不上。多选让同一个 auto-gpt 能同时给 Codex 和 Claude Code 用。新建默认只勾 Responses；一期已有的配置按当时自动判断的结果勾上。
- **格式转换交给渠道现有的适配器**：智能路由只负责读懂请求、打分、换模型名、改写思考力度；请求进入渠道后，由渠道适配器把它转成上游的格式，和直接用这种格式请求真实模型完全一样（例如 OpenAI 渠道把 Claude 格式转成 OpenAI 格式，`relay/channel/openai/adaptor.go:62-73`）。这推翻了一期「接口不一致直接拒绝、不做跨接口转换」的决定：一期担心转换会丢思考内容和工具调用字段，但这种转换是 new-api 现有功能，员工直接用 Claude Code 请求 GPT 模型时本来就走这条路。
- **Anthropic 格式换了渠道就去掉历史里的思考块**：沿用一期「渠道变了就清理加密思考内容」的思路。Anthropic 格式的思考块带签名，换到别的账号或别家模型后原样发过去可能被上游拒绝。这一条是推测，没有验证；实施时用 Claude 订阅渠道和 OpenAI 渠道之间来回换档实测，确认清理后上游不报错。
- **这期不做 Gemini 格式**：只有 7 种渠道能接收 Gemini 格式（OpenAI、Gemini、Vertex、Claude、NewAPI、高级自定义、智谱 4V），Codex 订阅、Claude 订阅、DeepSeek、AWS 等都直接拒收；Gemini 的模型名写在网址里，改动最大。用户 2026-11-05 决定不做。
- **保存时只拦渠道适配器明确拒收的格式**：依据是适配器代码里写死的「不支持」（例如 `relay/channel/codex/adaptor.go:24-29` 拒收 Claude 和 Gemini 格式，Codex 也拒收 Chat Completions），不会像元数据那样误判。用户 2026-11-05 选的。
- **Codex 订阅渠道不收 Anthropic 格式，这期接受**：问题在 Codex 渠道本身不支持这种格式，不在智能路由。给 Claude Code 用的虚拟模型，档位选 Claude 订阅或 API 渠道。让 Codex 渠道接收 Anthropic 格式以后作为单独需求再做。
- **配置弹窗：左栏竖排「打分 · 档位 · 顾问」，档位里再分三档**：用户先后看了「顶部 Tab」「左列表 + 右详情」「折叠摘要」「上中下三块」「两层切换」等布局，最后定为左栏竖排加三档切换。理由是注意力有限，一次只看一组设置；打分和顾问不该和三个档位连在一起。
- **默认档放在「档位」里**：默认档在打分失败或超时、打分把握不足、工具续跑没有会话、选中的档位没有渠道这 4 种情况下都会用到（`service/smartroute/rules.go:125-126,176,189-190`，`middleware/smart_route.go:149-150`），它是三个档位的兜底，不属于打分。
- **分组改成一行紧凑小标签，拖动排序**：用户嫌原来的分组组件太占地方。做法是给现有的分组顺序组件加一种紧凑样式，增删、排序、最多 5 个的规则不变；排序用拖动，不放箭头按钮。
- **说明文字收进字段名旁的 ⓘ**：用户嫌灰字太多抓不住重点；框里只留出错的红字和「不支持思考」这类必须一眼看到的状态。
- **虚拟模型进 `/api/user/models`，排在真实模型后面**：后台的选模型下拉都读这个接口，补上一处就都能选到。价格页、模型定价、档位模型下拉、渠道配置照旧不放虚拟模型：虚拟模型自己没有价格，也不能套用另一个虚拟模型。
- **演练场只列勾了 Chat 的虚拟模型**：演练场只会按 Chat Completions 格式发请求（`router/relay-router.go:69`），其他的选了一定报 400。
- **CC Switch：Claude、Codex 应用列出全部虚拟模型，Gemini 应用不列**：用户要求三个工具都能选；不做 Gemini 格式后，Gemini 下列出来一定用不了，用户 2026-11-05 改为不列。
- **打分请求在 Codex 渠道上不设输出上限**：本分支已修（commit 05d142f12）。Codex 上游不接受 `max_output_tokens`，打分只靠超时和最低思考力度控制长度。一期 PRD 02 C6 写的「输出上限 300 token」只对其他渠道成立。
- **质疑结论**：值得做。固定力度在同一档里浪费或不够；能力配错会让上游直接报错；Claude Code 员工用不了虚拟模型；这些都没有现成功能可以替代。
