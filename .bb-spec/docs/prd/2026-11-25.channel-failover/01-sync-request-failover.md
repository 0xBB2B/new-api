# 同步请求依次试完所有渠道

## 用户故事
### P0：作为调用 API 的用户，我想要某个渠道失败时网关自动换别的渠道，以便只要还有一个渠道能用，我的请求就能成功

**用例（主路径）**
- 场景：令牌分组 `default` 下，模型 `m1` 有 4 个启用的渠道：A 是 Claude 订阅渠道，优先级 0；B 是 ChatGPT 订阅渠道，优先级 0；C 是 OpenAI 渠道，优先级 10；D 是 OpenAI 渠道，优先级 5。每个渠道只有一个密钥，「失败重试次数」为 0。
- 操作：A、B、C 都返回 HTTP 500，D 正常回复。用户发一个流式对话请求，模型 `m1`。
- 预期：用户收到 D 的正常回复。A、B 先被试过（两者谁先谁后不限），然后是 C，最后是 D，每个渠道只被请求一次。服务器日志里的重试记录列出这 4 个渠道。

**用例（开场事件后失败）**
- 场景：A 返回 HTTP 200，先发 `response.created`，紧接着发 `response.failed`；B 正常。
- 操作：用户发一个流式 Responses 请求。
- 预期：用户收到的是 B 的完整回复，开头是 B 的 `response.created`，A 的事件一个都没收到。Claude 流里 A 先发 `message_start` 再发 `error`、Chat 流里 A 第一个数据块就是错误，结果相同。

**用例（全部失败）**
- 场景：主路径的 4 个渠道都返回 HTTP 500，D 返回的错误消息是 `upstream D down`。
- 操作：发同样的请求。
- 预期：4 个渠道各被请求一次，用户收到状态码 500，错误消息里有 `upstream D down`；收到的不是"没有可用渠道"。

**用例（已经给出正文）**
- 场景：A 先输出一段文字再断开，B、C、D 正常。
- 操作：发流式对话请求。
- 预期：用户收到 A 的那段文字，接着收到一个错误；B、C、D 都没被请求。

**用例（不换渠道的错误）**
- 场景：「自动重试状态码」为默认列表，A 返回 HTTP 400。
- 操作：发请求。
- 预期：用户收到这个 400，B、C、D 都没被请求。

**用例（只有一个渠道）**
- 场景：模型 `m2` 只有一个渠道 E，只有一个密钥，E 返回 HTTP 500，「失败重试次数」为 3。
- 操作：发请求。
- 预期：E 只被请求一次，用户收到 E 的 500。

**用例（多密钥渠道）**
- 场景：模型 `m3` 只有一个 Claude 订阅渠道 F，里面启用了 3 个密钥 k1、k2、k3；k1、k2 返回 429，k3 正常。
- 操作：发请求。
- 预期：用户收到正常回复；k1、k2、k3 每个最多被用一次。

### P0：作为管理员，我想要订阅渠道总是先被试，以便先用掉不额外花钱的订阅额度，最后才用按量计费的 API

**用例（主路径）**
- 场景：模型 `m1` 有 Claude 订阅渠道 A（优先级 0）和 OpenAI 渠道 C（优先级 100），两个都正常，没有渠道亲和记录。
- 操作：连续发 10 个请求。
- 预期：10 个请求都由 A 处理，C 没被请求。

**用例（渠道亲和）**
- 场景：同一个会话上次走的是 C，非严格的渠道亲和规则命中 C。
- 操作：C 返回 500，发请求。
- 预期：先试 C，再试 A。

### P1：作为使用 auto 分组的用户，我想要一个分组的渠道全部失败后，按令牌设置换到下一组

**用例（主路径）**
- 场景：令牌用 auto 分组，分组顺序是 `g1`、`g2`，令牌开了跨组重试。`g1` 下 `m1` 有 OpenAI 渠道 C 和 Claude 订阅渠道 A；`g2` 下有 ChatGPT 订阅渠道 B。A、C 都返回 500，B 正常。
- 操作：发请求。
- 预期：先试 A，再试 C，然后换到 `g2` 试 B；用户收到 B 的正常回复。
- 同一场景下令牌关掉跨组重试 → A、C 试完后，用户收到 C 的错误，B 没被请求。

## 约束
- C1：同步请求包括 OpenAI、Claude、Gemini、Responses 各种格式的对话，以及向量、图片、语音、重排，还有 Responses WebSocket、Realtime 的建连。这类请求在上游还没给出任何正文时失败，并且现有判定认为可以重试，网关就换一个本次请求里还没试过的渠道或密钥再发。Responses WebSocket、Realtime 只在连接上游失败时换。
- C2：Responses、Claude、OpenAI Chat 三种格式的流式回复里，开场事件网关先不发给客户端，等到正文开始再按原来的顺序一起发出。开场事件只认这份名单：Responses 的 `response.created`、`response.in_progress`、`response.queued`；Claude 的 `message_start`、`ping`；Chat 流里没有文字、思考、工具调用、结束原因和用量的数据块（通常只带 `role`）。名单外的事件一律算正文开始。正文开始之前上游报失败（Responses 的 `error`、`response.failed`、`response.error` 或 `response.status` 为 `failed`；Claude 的 `error` 事件；Chat 流里带 `error` 的数据块），按 C1 换渠道，客户端收不到这次尝试的任何事件。
- C15：正文开始之前上游结束了流：收到过终止事件（Responses 的 `response.completed`、`response.done`、`response.incomplete`，Claude 的 `message_stop`，Chat 流的 `[DONE]`），就补发扣住的事件和终止事件，按正常结束处理；没收到终止事件就断开（包括一个事件都没有），算失败，按 C1 换渠道。
- C16：一次尝试在正文开始前失败后，它的用量、工具调用次数、图片数都不计入结算；最终结算只用成功那次尝试的数据。
- C3：一次请求里，每个渠道的每个启用密钥最多被用一次。单密钥渠道失败一次就算试过；多密钥渠道里的每个启用密钥都试过以后，这个渠道才算试过。
- C4：同步请求不受「失败重试次数」限制。能选的渠道和密钥都试过以后才停下，然后返回错误，不再从头重试。
- C5：所有尝试都失败时，返回给客户端的是最后一次尝试的错误（状态码和错误内容），不是"没有可用渠道"。
- C6：渠道类型是 Claude 订阅或 ChatGPT 订阅的，叫 subscription channel（订阅渠道）；Sub2API 和其他类型都不算。同一分组内，先把还没试完的订阅渠道试完，再试其他渠道；第一次选渠道也遵守这个顺序。
- C7：订阅渠道之间、其他渠道之间，都按优先级从高到低试；优先级相同的按权重随机。
- C8：非严格的渠道亲和命中某个渠道时，第一次先试这个渠道，不管它是不是订阅渠道；它试完以后，剩下的按 C6、C7 的顺序试。
- C9：auto 分组时，C6、C7 在每个分组内各自生效。令牌开了跨组重试，一个分组里能选的渠道全部试完后，才换下一个分组；没开时，第一个选中的分组试完就停。
- C10：上游已经给出正文之后失败，不换渠道，把错误发给客户端。心跳不算正文。
- C11：现有判定认为不能重试的错误不换渠道，直接返回。这些错误包括：不在「自动重试状态码」列表里的状态码（默认列表不含 400、408）；始终不换的 504、524 和上游返回内容解析失败；带"跳过重试"标记的错误。
- C12：会话绑定（严格模式）和令牌钉死渠道的请求，失败后不换渠道。这和现在一样。
- C13：可选的渠道还要满足现有的过滤条件，比如智能路由的请求格式过滤，以及渠道启用状态。本次请求中途被自动禁用的渠道或密钥，也不会再被选中。
- C14：第一次选渠道就选不到时，报错和现在一样。

## 验收
- [ ] C1：分别用对话（流式、非流式）、向量、图片请求复现主路径，前几个渠道返回 500、最后一个正常 → 都拿到正常结果；Responses WebSocket 前几个渠道建连失败、最后一个能连上 → 连接成功
- [ ] C2：Responses 流（`response.created` 后接 `response.failed`）、Claude 流（`message_start` 后接 `error`）、Chat 流（第一个数据块是错误）三种情况，都换到下一个渠道，客户端收到的事件里没有第一个渠道的内容；正常请求里，客户端收到的事件顺序和内容与改动前一致
- [ ] C3：同一优先级有 3 个单密钥渠道、前 2 个被选中的都失败 → 第 3 次选中的是剩下那个；多密钥用例里每个密钥最多被用一次，k3 最终成功
- [ ] C4：「失败重试次数」为 0，5 个渠道里前 4 个失败 → 第 5 个被请求，并返回成功；只有一个渠道的用例里，E 只被请求一次
- [ ] C5：全部失败用例里，客户端收到的状态码和错误消息都来自最后一次尝试
- [ ] C6：订阅渠道优先级 0、OpenAI 渠道优先级 100 → 第一个被请求的是订阅渠道；Claude 订阅、ChatGPT 订阅两种类型都按订阅渠道处理，Sub2API 不算
- [ ] C7：2 个订阅渠道的优先级分别是 10、5，都失败 → 先试优先级 10 的那个
- [ ] C8：渠道亲和用例里，先试 C，再试 A
- [ ] C9：auto 分组用例，开跨组重试 → 依次试 A、C、B；关跨组重试 → 只试 A、C
- [ ] C10：已经给出正文的用例里，后面的渠道没被请求，客户端收到一个错误
- [ ] C11：默认列表下，首个渠道返回 400 或 504 → 不换渠道，客户端收到原状态码；把 400 加进列表后，首个渠道返回 400 → 换渠道
- [ ] C12：令牌钉死渠道 A，A 返回 500 → 不换渠道，客户端收到 500
- [ ] C13：A 失败并被自动禁用，B 也失败 → A 不会被再次选中
- [ ] C14：模型没有任何可用渠道 → 返回的报错和改动前一样
- [ ] C15：A 只发 `response.created` 再发 `response.completed`（没有正文）→ 客户端收到这两个事件，B 没被请求；A 只发 `response.created` 就断开 → 换到 B；A 一个事件都没发就断开 → 换到 B；Claude 流 `message_start` 后接 `message_stop`、Chat 流只有 role 块后接 `[DONE]`，结果同第一种
- [ ] C16：A 在正文前失败前已经上报过 1 次内置工具调用，B 成功且上报 2 次 → 结算按 2 次；A 失败、B 成功时，消费日志里只有一条成功记录，金额只按 B 的用量算

## 验证路径
1. 用 mock 上游配 4 个渠道，按主路径设置好，发流式对话请求 → 收到 D 的回复；mock 记录显示 A、B、C、D 各被请求一次，C 在 D 之前。
2. 让 D 也返回 500 → 收到 D 的 500 和 `upstream D down`。
3. 让 A 发 `response.created` 后接 `response.failed`，发流式 Responses 请求 → 客户端只看到 B 的事件。
4. 让 A 先输出正文再断开 → 后面的渠道都没被请求。
5. 让 A 返回 400 → 后面的渠道都没被请求。
6. 配一个有 3 个密钥的订阅渠道，前 2 个返回 429 → 第 3 个密钥成功。
7. 换成 auto 分组，按 P1 用例分别打开、关闭跨组重试 → 被请求的渠道顺序符合预期。
