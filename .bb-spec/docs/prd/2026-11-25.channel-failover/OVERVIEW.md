# 上游失败时依次试完所有渠道

## 背景与问题
管理员给同一个模型配了好几个渠道：有 Claude 订阅、ChatGPT 订阅这类订阅渠道（按月付费，用了不额外花钱），也有按用量计费的 API 渠道。某个渠道出错时，客户端经常直接收到报错，可是同一个模型明明还有别的渠道能用。

现在的重试有四个缺口：

- 重试次数由系统设置「失败重试次数」决定，默认是 0，也就是默认不重试。
- 第 N 次重试挑第 N 高的优先级档，同一档里按权重随机挑。已经失败过的渠道和密钥不会被排除，所以可能连着选中同一个坏渠道；超过档数以后，会一直在最低一档里打转。
- 上游流式回复通常先发一个开场事件，再发正文。上游发完开场事件就报失败时（比如 Responses 的 `response.failed`），网关已经把开场事件转给了客户端，算作"已经输出"，不会再换渠道。2026-11-13 到 11-19 这 7 天，生产环境记到 842 次 `response.failed`。
- 2026-11-18 起，生产环境最终报给客户端的错误里，排前两位的是 `OAuth access token has expired`（37 次，订阅渠道的令牌过期）和 `Codex is at capacity`（20 次）。这两种都发生在输出之前，换一个渠道就能接着服务。
- 重试顺序只看管理员填的优先级，跟渠道是订阅渠道还是 API 渠道没有关系。管理员只能靠手动把订阅渠道的优先级调高，新加的订阅渠道容易被忘掉。

## 目标
- 同步请求在上游还没给出任何正文时失败，网关会换到下一个还没试过的渠道或密钥。失败的形式包括上游直接返回错误状态码，也包括流式回复里先发了开场事件、接着就报失败。提供该模型的渠道和密钥都试过一遍、全部失败后，才把错误返回给客户端。
- 换渠道时先试 subscription channel（订阅渠道），再试其他渠道。
- 系统设置「失败重试次数」只管 async task（异步任务）。设置页的标签和说明讲清楚这一点，也讲清楚其他请求是怎么换渠道的。

## 非目标
- 上游已经给出正文（文字、思考、工具调用）之后再断开：照旧把错误发给客户端，不换渠道。
- Responses WebSocket、Realtime 这两种长连接：仍然只在连接上游失败时换渠道；连上以后上游报失败，照旧发给客户端。
- 哪些错误会换渠道：按「自动重试状态码」列表来，渠道级错误照旧会换；504、524 和上游返回内容解析失败照旧不换；默认列表里没有 400、408。流式回复里的错误事件只带错误类型、没有状态码时，`invalid_request_error` 类型和"输入过长"这类请求本身的错误记为 400，其余记为 500。
- 会话绑定（严格模式，同一会话固定走同一渠道）、令牌钉死渠道这两种情况：照旧不换渠道。
- 异步任务（视频生成这类先提交、过后再取结果的请求）：重试次数和换渠道的方式不变，仍按「失败重试次数」重试，也不排除试过的渠道和密钥。订阅渠道不提供异步任务用的模型，所以"先订阅"的排序对异步任务没有影响。
- Gemini 格式的客户端：上游直接返回错误状态码时会换渠道。上游也是 Gemini 时，流式回复里的失败照旧发给客户端，回复不经过开场事件的扣留（Gemini 上游没有开场事件）。上游是 Claude 或 Responses 格式、转成 Gemini 格式发给客户端时，开场事件照样扣留，正文前的失败照样换渠道。
- 不限制一次请求总共能等多久。
- 不新增"订阅渠道"的配置开关。哪些算订阅渠道，按渠道类型固定判定。
- 计费：扣费、预扣和退款的规则都不变。
- 顾问档把思考力度 `none` 原样透传、引起的 400：另开需求处理。

## 整体验证路径
1. 用 mock 上游（模拟上游的测试服务）给模型 `m1` 配 4 个渠道：A 是 Claude 订阅渠道，优先级 0；B 是 ChatGPT 订阅渠道，优先级 0；C 是 OpenAI 渠道，优先级 10；D 是 OpenAI 渠道，优先级 5。A、B、C 都返回 500，D 正常回复。「失败重试次数」设为 0，发一个流式对话请求 → 客户端收到 D 的正常回复；按时间顺序，A、B 被试过（两者谁先谁后不限），然后是 C，最后是 D，每个渠道只被请求了一次。
2. 让 D 也返回 500，再发一次 → 客户端收到的是 D 返回的那个 500 错误，不是"没有可用渠道"；四个渠道各被请求了一次。
3. 让 A 发出开场事件 `response.created` 后紧接着发 `response.failed`，B 正常，发一个流式 Responses 请求 → 客户端只收到 B 的完整回复，看不到 A 的任何事件。
4. 让 A 先输出一段正文再断开，B、C、D 正常 → 客户端收到 A 的那段正文和一个错误，B、C、D 都没被请求。
5. 打开系统设置 → 请求策略 → 会话与重试 → 重试预算卡片，第一个字段显示「异步任务最多重试次数」和新的说明文字；切到英文界面，显示对应的英文。
6. 「失败重试次数」设为 1，提交一个视频任务，让第一个渠道失败 → 只重试 1 次，跟改动前一样。

## 决策记录
- **只管上游给出正文之前的失败**（用户 2026-11-25 选定）。正文发出去以后，要想续上只能把上游的完整回复先攒在网关、不边收边发，这会让流式回复变成等全部生成完才一次性返回，首字延迟变得很长。被否决的方向：中途断流也换渠道续上。
- **开场事件先扣住，等到第一段正文再发**（用户选定）。上游在开场事件和正文之间报失败，推测是"对话中断"的常见样子之一（背景里的 842 次 `response.failed` 没有记下失败发生在正文前还是正文后，未验证）。开场事件一旦发给客户端，就算已经输出、不能换渠道了，所以要在网关先扣住它。代价：开场事件会晚一点发出（推测通常不到 1 秒，未实测）。被否决的方向：只在 HTTP 层失败时换渠道，这样上面那类失败仍会直接报错。
- **只有开场事件就结束时，按有没有终止事件分开处理**（用户选定）。没有终止事件就断开，说明上游出了问题，算失败、换渠道；有终止事件只是没有正文，可能就是模型的真实回答（比如被内容审核拦了），换渠道多半还是空的，所以补发扣住的事件，按正常结束处理。被否决的方向：只要没有正文就换渠道；都补发、和现在一样。
- **开场事件按名单认定，名单外的事件一律算正文开始**。这样做宁可早一点放行，也不会把正文误扣住。代价：上游先发了名单外的前置事件（比如空的 `response.output_item.added`）再失败时，换不了渠道。
- **正文前失败只在确定会换渠道时才扣下，最终失败和以前一样**（用户 2026-11-25 选定）。实现中发现：按次固定价的模型，以前上游在开场事件后报失败时照常收这一次的费用，客户端看到的是 200 流里的 `response.failed`。这次需求只要求"能换就换"，没要求改客户端看到的格式和失败计费规则，所以不会换渠道时（错误不可重试、或已经没有可试的渠道和密钥），客户端看到的和计费都与改动前一致；只有中间被换掉的尝试不收费。被否决的方向：最终失败也改成返回 HTTP 错误、全部退款，这样会改变 Codex CLI 等客户端看到的错误格式，也会让按次固定价的失败请求不再收费。
- **长连接只在建连失败时换渠道**。Responses WebSocket 一条连接上会连续跑多个请求，连上以后就锁定了渠道；要在连上之后换渠道，得重建上游连接、重放之前的请求，改动和风险都超出这次范围。
- **订阅渠道按渠道类型自动判定**（用户选定）：渠道类型是 Claude 订阅或 ChatGPT 订阅（渠道表单里叫 ChatGPT Subscription (Codex)）的就算订阅渠道。这样管理员不用记着给每个订阅渠道调优先级，新加的订阅渠道也不会被排到后面。被否决的方向：不改代码，靠管理员把订阅渠道的优先级调高，差别只在"订阅渠道排在前面"这件事由谁保证。Sub2API 不算订阅渠道：代码里它只用 API key 访问对方的网关，没有订阅账号的凭据。
- **订阅渠道总排在前面**，哪怕 API 渠道的优先级更高。代价：订阅账号的限额用完、又还没被自动禁用时，每个请求都会先在它身上失败一次，再换到下一个渠道，多等一次往返。
- **每个渠道、每个密钥最多试一次，试完全部才报错**，不受「失败重试次数」限制（用户选定）。这是"所有渠道都试过才报错"的直接要求。代价是渠道多又都坏了的时候，客户端要等很久才拿到错误。被否决的方向：排除失败过的渠道，但仍受次数上限限制。
- **多密钥渠道里每个启用的密钥各试一次**（用户选定）。每个密钥背后是独立的上游账号，一个账号限额用完，不代表同一渠道的其他账号也不行。被否决的方向：多密钥渠道失败一次就算整个渠道试过。
- **全部试完后直接报错，不再从头重试**（用户选定）。这样等待时间可以预期。代价：只有一个渠道、一个密钥时，临时的 429 或 5xx 不会再像现在这样被重试几次。被否决的方向：试完后按「失败重试次数」再从头轮几遍。
- **全部失败时返回最后一次尝试的错误**。原因：客户端和管理员要看到的是上游真实的失败原因，"没有可用渠道"什么信息都没有。
- **渠道亲和选中的渠道先试**（用户选定），哪怕它是 API 渠道；它失败后，再按先订阅、后其他的顺序试剩下的。原因：中途换渠道会丢掉上游的上下文缓存，长对话里这笔缓存费往往比订阅省下的还多（推测，未测算）。被否决的方向：订阅优先压过亲和。
- **沿用现有的错误判定**（用户选定）。400 多半是请求本身有问题，换了渠道也一样失败；超时类错误（504、524）要是每个渠道都等一遍，客户端要等好几倍的时间。管理员仍可以自己改「自动重试状态码」列表。被否决的方向：504、524 也换渠道。
- **流式错误事件里的请求错误记为 400**（2026-11-26 审查时发现，按修复建议改）。流里的错误事件只带错误类型，以前一律当 500，"输入过长"这类错误会在每个渠道上重放一遍，最后才报错；改动前客户端是直接收到失败事件的。按错误类型 `invalid_request_error` 和已知的请求错误码记为 400，就不会换渠道。
- **auto 分组时，每个分组内先订阅后其他**，令牌开了跨组重试，才在这个分组的渠道全部试完后换下一组（用户选定）。原因：分组顺序是管理员按价格倍率排的，客户付多少钱不应该因为重试顺序而变。被否决的方向：跨所有分组先把订阅渠道试一遍。
- **会话绑定（严格模式）、令牌钉死渠道照旧不换**（用户选定）。这两种都是明确要求只走某个渠道，换了渠道就违反了这个要求。
- **适用于所有同步请求**（用户选定）：对话、向量、图片、语音、重排，以及 Responses WebSocket、Realtime 的建连。它们本来就共用同一套重试判定，只给对话开小灶反而要多加分支，同一个设置也会更难讲清楚。被否决的方向：只管对话类请求。
- **「失败重试次数」只管异步任务**（用户选定）。任务提交一次就可能扣上游厂商的钱，不在这次要解决的问题里。被否决的方向：任务也改成试完全部渠道，并删掉这个设置。
- **设置页文案**（预览页已经用户确认）：标签加上"异步任务"；说明写一段，"订阅渠道"写明是 Claude 订阅和 ChatGPT 订阅两种。原因：同一个页面上已经有"优先订阅"，指的是用户套餐，只写"订阅渠道"容易混。被否决的方向：两段式说明、只写"订阅渠道"的短写法。2026-11-26 审查时发现说明没写"当前分组里"和"每个密钥各试一次"，容易让人以为会跨所有分组试、多密钥渠道只试一次，用户确认了新预览：说明补上分组范围、按密钥各试一次，以及 auto 分组要开「跨分组重试」才换下一组。
- **质疑结论**：把订阅渠道的优先级调高、再把重试次数调大，今天就能大致做到"先订阅、后 API"。但这样补不上三个缺口：失败过的渠道还会被再选中；重试次数是写死的，不会"把所有渠道都试一遍"；开场事件之后的失败不会换渠道。所以这次需求值得做。
